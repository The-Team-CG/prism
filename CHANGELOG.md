# Changelog

Notable project changes are recorded here for people upgrading or contributing.
The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
and the project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- PMCM can open drafts in the new Pascal-based floor plan editor when `NEXT_PUBLIC_PRISM_FLOORPLAN_ENGINE=pascal`; existing layouts convert on first open, and the first save stores the converted layout. Without the flag the current editor opens as before. In both editors a submitted or approved draft now opens read-only, since the API already refused saves to it. Plans gain `scene` and `scene_format` columns (migration `20261124090000_floorplan_floor_plan_scene`, apply before deploying the API); `PUT /plans/:planId` accepts a `scene`, checks it and the seating rules, and refuses one sent with `objects`; submitted and approved snapshots carry the scene. New package `@prism/floorplan-scene`; `@prism/floorplan-canvas` gains `/editor` and `/plugin` (ADR-0010).
- Every portal has an Account page, first in the account menu (`/dashboard/account`; the coordinator portal's `?view=account`). It heads with who is signed in, then lists each setting as a row with its value now: name and email, password, two-step sign-in (required for PMCM staff), devices, the latest sign-in and notification channels, and for clients and suppliers their PMCM contact and a Privacy summary. Nothing is edited in place: a row opens its one task in a side panel that fills the screen on phones, and a banner appears only when sign-ins failed since the last visit. Suppliers get a link to their supplier record and PMCM admins to "Workspace settings" (the sidebar's former "Settings"). The client workspace carries `pmcmContacts` and `auth/me` returns `lastSignInAt`.
- People can change their own name and, while signed in, their password (current password first; it signs out every session), and see their last 10 sign-ins with the browser and whether each worked. Routes `PATCH auth/me`, `POST auth/me/password` and `GET auth/me/sign-ins`; a wrong current password counts toward the sign-in lockout and is a 403, so the portal does not sign the person out.
- A Devices row shows where the person is signed in ("This device and 2 others") with when each browser was last active. Any other device can be signed out on its own, or all of them with "Sign out everywhere else". Sign out in the menu now ends only this device; a session from before this release still ends every session. Each sign-in records its browser in the new `identity_access.user_sessions` table (migration `20261121090000_identity-access_user_sessions`, apply before deploying the API), the session token carries that row's id, and the guard refuses a token whose device was signed out. Routes `GET auth/me/sessions`, `DELETE auth/me/sessions/:sessionId` and `POST auth/me/sessions/sign-out-others`.
- Clients, suppliers and coordinators can turn on two-step sign-in from Account: they confirm their password, scan a QR code (or type the key) into an authenticator app, and it turns on only once a code from that app is confirmed. Signing in then asks for the six-digit code after the password on the client, supplier and event portals; a wrong code can be retried, an expired one goes back to the password. They turn it off with their password; PMCM staff keep it on. PMCM's account list shows who has it on, and "Reset two-factor" now works for any account. New column `identity_access.users.two_factor_pending_secret` (migration `20261122090000_identity-access_two_factor_pending_secret`, apply before deploying the API) and routes `POST auth/me/two-factor/setup`, `/enable` and `/disable`. The six-box code input moved to `@prism/ui/authenticator-code-input`.
- People can change their sign-in email from Account: they enter the new address and their password, a link goes to the new address and a notice to the current one, and the Email row shows the change waiting until the link is opened (they can send it again or withdraw it). Opening the link on any portal's `/confirm-email` page switches the account in one transaction and signs it out everywhere; everything that recognises the person by email moves with it, so a client keeps their events, a supplier their supplier record, and notifications, message threads, the notification inbox and privacy requests follow the new address. Signatures, audit entries and sign-in history keep the address they were made with. If another account took the address meanwhile, nothing changes. New table `identity_access.email_change_requests` (migration `20261123090000_identity-access_email_change_requests`, apply before deploying the API) and routes `POST`/`DELETE auth/me/email` and `POST auth/email-change/confirm`.
- Events and bookings are cards instead of tables. Each card shows the event day as a date tile, how far away it is, a six-step stage track from inquiry to closure, what is waiting and the money, plus Billing, Files and Messages shortcuts with what is waiting there. PMCM Events opens on "Needs you": each card lists the Inbox's own items for that event, so the list and the Inbox agree, then Coming up and Done, with Archive as one more tab. A supplier's bookings lead with the next step and a button that does it (confirm the booking, acknowledge a schedule), when and where to arrive and the next payout; finished bookings move to Done. A client sees their next event large with the days to go and their next step, and their other events as cards. New `GET /pmcm/event-attention` returns the Inbox's items grouped by event (`?eventId=` for one event's full list).
- Every event has a cover. A cover is drawn from the event's type (corporate, conference, gala, product launch, celebration, workshop), and PMCM can make any image in an event's files its cover ("Use as event cover" / "Remove as event cover"); clients, booked suppliers and coordinators see it. Events now carry their inquiry's type (`eventType`) and an optional `coverObjectId`, with `PATCH /events/:id/cover` for PMCM and `GET /events/:id/cover` for anyone who can read the event (migration `20261119090000_event-lifecycle_event_type_and_cover`).
- The client home, the supplier's Today page, a supplier's opened booking and both event overviews open with the same dark card over the event's cover: the step or event, one large countdown (days overdue, left or to go), and a footer with what to do beside its button. For PMCM the card also shows the stage, when the client last opened the portal with their unread notices, the portal status and guest code, and an overview adds "Needs you" (how long each item has waited, red once overdue), readiness with what holds the score back, "Coming up" for the next 30 days and nine area tiles with their counts. Clients get a "Get started" row for a new event, what is new since their last visit, a floor plan card that walks from their ideas to the approved layout, and a payments card. `GET /pmcm/events/:eventId/client-activity` returns the client's last sign-in and unread notices.
- The PMCM Inbox, the client home and the supplier's Today list work in the same rows (`@prism/ui/action-list`): an icon coloured by urgency, the step and its event, a due or status column, and the action. Several of the same step fold into one row that opens to list them.
- Notifications are one screen on every portal. It opens on what asks the reader to confirm receipt, with its deadline and an Acknowledge button, then lists every notice by day with its event, the time, an unread dot and a link to the exact item. Opening a notice marks it read; Mark all read, an Unread filter and "Show older notifications" (up to the 200 newest) sit with the list. Channel settings (email and Viber) are in a side panel. PMCM gets a Notifications page and navigation item instead of a Settings tab, every portal shows an unread count on it, and a coordinator's notice opens their shift or run sheet. The inbox API returns the event name, the unread total and a growable page size. Billing-statement notices, one per payment milestone, open the event's Billing page.
- Messages opens as one inbox across events for PMCM, clients and suppliers, with the event named on each conversation (an event's own Messages tab still shows only that event). People see each other's names, never emails. Lists page from the server, search covers subjects, event names and message text, and unread counts reach every open conversation. Conversations refresh every 15 seconds while the tab is visible, and the Messages navigation item shows an unread count. `GET /communication/inbox` returns the account's conversations with their latest message.
- Each new message notifies the other members by email and, where linked, Viber, naming the sender and conversation and quoting the start of the message; the in-portal notice opens the conversation after sign-in, and channel copies combine in the inbox while each delivery keeps its receipt checks. Without a configured Viber bot, Viber notices are skipped instead of failing. Messages offers Viber linking when configured.
- Messages can carry up to 10 files, uploaded from a device or copied from the event's Files library; each is a copy only the conversation's active members can open. PMCM can add and remove members (added people get a notice and see earlier messages) and close or reopen a conversation; closed conversations take no new messages and move to a Closed list. Assigned coordinators read and reply to conversations they belong to without starting new ones. PMCM can see which members have read its messages; other roles' responses do not expose those read times.
- Files work the same on the client, supplier and PMCM portals (`@prism/ui/file-library`). Files starts on a card for each event with a bar of how many requested files are in and what is still needed or overdue; an event's Library has one "Needed from you" list that takes dropped files, one searchable table (type, name, from, added, size, status with any expiry, download) and one preview panel with the actions each role has. Clients also search across their events, download an event's files as one ZIP (a folder per category), see what PMCM added since their last visit, and send a copy of a file from another event; the copy is made by the server. The supplier's certifications sit on its start page as their supplier record, and the opened event is kept in the address so Back returns to the cards.
- PMCM's library puts files waiting for review first (preview, approve, reject with a reason, or approve several at once), then every file from the client, suppliers and PMCM with who sent it and where its review stands. The sender is told the outcome and, on a rejection, the reason; PMCM is told when a file arrives and sees each waiting file in the command inbox until it decides. A newer upload replaces the sender's earlier unreviewed file, so only the newest waits.
- Supplier Files shows what PMCM still needs first (drop a file on an item to send it; contracts link to their booking), then every booking document, contract version and certification with PMCM's review state, expiry warnings and an inline preview.
- Stored files can carry a "valid until" date, set by whoever sent the file or by PMCM. Libraries flag files expiring within 30 days or already expired (judged by Philippine calendar day, so the valid-until day itself is still valid), "Use existing" won't resend an expired document, a copy keeps its original's date, and the requirement reminder sweep tells the sender (and PMCM) once before a required file expires and once after.
- Uploads that never finished (requested or failed and untouched for three days) are listed apart from files and removed every six hours with their partial provider bytes; a later retry of the same upload still resumes. `PRISM_DISABLE_ABANDONED_UPLOAD_CLEANUP_JOB=1` turns the sweep off.
- PMCM has one set of payment details for the company: bank accounts, e-wallets (GCash, Maya) and a cheque payee, each with optional instructions, an on/off switch, an order and, for accounts, a PNG or JPEG QR up to 1 MB stored once per image. Finance has a Payment details page to edit them (saves check the revision the editor loaded, changing an existing account number asks first, a refused save names who saved in between, and a preview shows what the client will see). API `/api/payment-details` (PMCM finance only); migration `20261117090000_commercial_pmcm_payment_details` adds two commercial tables.
- Billing uses PMCM's payment details. A statement is issued with a copy of them and cannot be issued while none is turned on (the Billing sources tab warns and links to Payment details; the placeholder accounts are gone). A client's statement of account always shows the accounts that are on now and says when they changed after issue, and "How to pay" is a dialog (a bottom sheet on a phone) with the amount to send, the reference to write and a tab per account with copy buttons, instructions and a Save QR button. A client can load a QR only for their own event once the statement is sent. Migration `20261118090000_commercial_statement_payment_details_revision` adds a nullable column to billing statements.
- Client billing is one page across events: what is overdue and due in the next two weeks first (net of amounts under review), each event's payments as a progress bar, and every payment on a timeline with its state. An event's billing page leads with how much is paid and the one thing to know now, and lets the client report a payment with proof ("I've paid"); PMCM checks reported payments before they count, and the client sees them as being checked, or PMCM's reason when one is not accepted. The "amount to send" is everything overdue, or else the next payment, less amounts under review, transfers still being checked and credit PMCM holds. Once an event is paid in full its billing page lists every receipt for download. The old Statements, Payment schedule, Reminders, Receipts and Balance tabs are gone, and calendars colour payments by state (paid, late, still due).
- PMCM Finance opens on one desk across events instead of an event picker: totals for clients overdue, money to verify or apply, what PMCM owes suppliers and open disputes and corrections; a "Needs you" queue with search, filters by kind of work and counts, marks for work that arrived since the last visit, in-place verification (one payment or several with one note; each client is told) and reminders to late clients (once a day, logged on the payment); "What clients owe" and eight-week cash-outlook charts with table views; and "Download spreadsheet" for every client payment. Each client payment has a History panel with everything that happened to it, oldest first. The command inbox lists payments to check, disputes, corrections and late supplier payouts, and client payments only once overdue or due within two weeks. The stored statement PDF now downloads (it always said it was not ready).
- Billing documents are branded PDFs the API renders: the billing statement, the statement of account (live accounts and, for an account with a QR, where to scan) and each payment receipt, with line items, payment schedule, payment history, how to pay, and a "Paid in full" or "Received" stamp. PMCM sees a payment's proof inline with Verify beside it; a client sees a thumbnail before sending it. Billing tells the other side when something changes (a client when a reported payment is accepted or not, PMCM when one is reported, a supplier when money is sent), and the sidebars badge overdue payments, open Finance work and money a supplier has not seen.
- Supplier Payments leads with what PMCM has paid, the next payment and what is still to come, then each booking by event with its agreed amount and payouts on a bar and a timeline. Suppliers can confirm a payout reached them ("I received this") and attach their official receipt then or later; PMCM gets a notice and sees each release's confirmation and receipt, and a payout PMCM reversed cannot be confirmed. Migration `20261116090000_commercial_supplier_payout_receipts` adds four nullable columns to `commercial.supplier_payout_records`.
- The `portal-uat` seed covers every billing state (paid in full, overdue and disputed, part paid with a payment to verify and a rejected transfer, unpaid with unapplied money, a draft source), a late supplier payout, PMCM payment details with a stand-in QR, notices for Ana, XPERTO, Ms. Mys and Marco, a different event type per event and an on-track sixth event with a second XPERTO booking; it also locks the selected supplier quotes so payouts can be scheduled.
- Signed-in client, supplier, PMCM/coordinator and guest-pass pages share a soft pastel mascot-and-doodle background, with opaque cards and headers keeping event work readable.
- Clients can follow event milestones, submit briefing and layout preferences, review official floorplans, sign conformes and addenda, track billing, and request an ocular visit. PMCM retains ownership of official plans and event decisions.
- PMCM can plan events with versioned task templates, previewed date changes, supplier readiness and file requirements, event-day schedules, coordinator handoffs, and archive closeout records.
- PMCM finance can reconcile external receipts, apply and reverse payments, record refunds, review billing disputes, and attach private payment evidence. Clients can view published statements with payment and refund history.
- Guests can check in with consent, submit feedback within the event’s seven-day feedback window, and play event games. PMCM controls game sessions, moderation, retention, and event-scoped access.
- Signed-in users can view and acknowledge their own notices. PMCM can inspect provider outcomes, retry failed delivery, and escalate notices that miss acknowledgment deadlines. See the [operational communications runbook](docs/runbooks/operational-communications.md).

### Changed

- Clients and suppliers can download their own data straight away from Privacy ("Download my data now"), confirmed with their password: a JSON file of their account, inquiries, events and billing, the same export PMCM produces, recorded as a finished request in their history and audited. PMCM's privacy console is now tabs (Queue, Log a request, Legal holds, Retention); queue cards share the requester's type icon and due pill with one main action, and each retention rule reads as one plain sentence with On/Off, changed through an editor that keeps the reason with the change.
- Privacy is one screen for clients and suppliers. It lists requests first, each a compact row with a four-step track (Sent, Identity check, In progress, Done) and a due date that stays grey until the last week, opening its details and Cancel in a side panel; finished ones sit under Earlier. "New request" is a three-step dialog (what, details, confirm with the password, where a deletion's warning also sits). A request can be withdrawn until PMCM reviews it, the requester is notified when PMCM approves, closes or completes it, and the page shows which privacy notice they accepted and when.
- A client or supplier confirms a privacy request with their account password instead of an ID. The request records when identity was confirmed, its track moves past the identity check, and PMCM's console shows "Identity confirmed with the account password". A wrong password is refused without signing the person out and counts toward the sign-in lockout. No ID documents are stored. Adds `platform_ops.privacy_requests.identity_confirmed_at` and `identity_method` (migration `20261120090000_platform-ops_privacy_identity_confirmation`). Client component tests (`.test.tsx`) now run too; they had been left out of the client's test config.
- The calendar reads the same on every portal, with Month, Week, Day (a single-date agenda, optional time grid) and Agenda views; weekends are lightly textured and event blocks tinted. Each entry names its event after what is due ("Balance due · Gala"); highlights are titled "Overdue and up next", put anything overdue first and keep the next event day with its picture; and the panel an entry opens shows the event's picture, a countdown, the same facts layout and the event's other entries. An empty month links to the last and next entries. The calendar keeps its category, view, date and done filter in the address (`?kind=…&period=week&date=…&open=1`), so links and refreshes open the same place; older links to payments, site visits, event dates or layout approvals open it filtered to that kind.
- The PMCM Files start page, where an event is chosen, shows each event as the same card as on Events, with how many file requirements are met and, in orange, how many are open or overdue. The client's event Documents tab is now Files and shows the same library.
- A client's Billing & Payments and a supplier's Payments share their figures and event cards (`MoneyTile`, `PaymentEventCard` in `@prism/ui/payment-track`). The supplier page is titled Payments, like its menu item.
- Page titles on the client, supplier and PMCM portals are plain text on the same left edge as the page's content. Portal audit fixes put Music in the top bar, keep mascot backgrounds quiet behind headings, and improve mobile tabs, tables and assignment cards; PMCM navigation removes placeholder views and separates archives.
- The four portals use shared page and transport patterns while preserving role-specific workflows. New portal HTTP calls use `@prism/api-client` from feature data adapters; shared write contracts use Zod schemas in `@prism/types`. Signed-in screens also share a neutral visual system and role-specific navigation.
- Cross-context writes use owner capabilities, and role-scoped reads compose through `read-models`. Archived events remain available for authorized history, while operational writes are blocked.
- Local and deployment setup use one canonical `DATABASE_URL`; local fixtures run only through guarded seed commands. See the [environment and fixture runbook](docs/runbooks/environments-and-fixtures.md).
- The pre-production migration history uses seven owner-scoped schema baselines instead of 102 folders. Existing databases must not adopt the replacement history without a verified backup and approved rebuild; replacing migration history does not alter an existing database. See the [database migration runbook](docs/runbooks/database-migrations.md).
- The inquiry-category migration maps legacy `Private` values to `Individual`; `School` and `Other` remain readable. Existing UAT fixture dates may retain prior local-midnight values until reseeded.
- AI data handling and activation prerequisites are defined in the [AI data policy](docs/product/ai-data-policy.md); provider-specific qualification gates are in the [provider-routing runbook](docs/runbooks/ai-provider-routing.md).
- Consolidated the documentation bundle and this changelog's unreleased section: removed the superseded feature-ledger delivery overlay and the duplicate feature map and outcomes tables in the actual-system document, and brought the ledger, architecture, accounts and communications guidance up to date with the Account, billing, files, messages and notification work.

### Fixed

- The guest portal's tests now include `.tsx` files, as the client, supplier and event portals do, and guest declares the jsdom and Testing Library packages its view tests already used.
- PMCM's "Share a file" on an event's Files page works. Storage refused every file PMCM shared ("Storage owner reference is not supported for this usage"); a file PMCM shares is now accepted from PMCM only and visible to the client, not to suppliers or coordinators.
- "Show older notifications" stops at the 200 newest notices instead of failing with an error after six clicks, and a notification list that cannot load now says so and offers Try again instead of saying there are no notifications.
- Billing balances reflect recorded payments, and signing a conforme no longer creates fabricated billing. Idempotent command replays do not duplicate event decisions, audit records, notifications, or event-day logs.
- Audit hash verification matches PostgreSQL JSONB ordering and accepts valid legacy chains. A mismatched historical chain still blocks writes and requires integrity review; see the [audit-chain repair runbook](docs/runbooks/audit-chain-repair.md) before repair.
- Public and role-scoped responses enforce event access and omit private PMCM details. Sensitive mutations require a verified actor and event scope; authentication and public entry points have rate limits and session protections.

### Security

- The CI dependency audit (`scripts/npm-audit-ci.mjs`) can tolerate a named advisory until a set date when it has no fixed release. It now tolerates only GHSA-fc5q-39xc-vjpf (picomatch, used by dev tooling and absent from the production dependency tree) until 2026-12-18; every other advisory at moderate or above still fails CI, and the exemption fails CI again once its date passes.
- Privacy exports, corrections, and account erasure require approved, scoped requests. Legal holds block matching erasure, staff account erasure is refused, and audit records retain metadata rather than exported record contents.
- File access checks event scope, visibility, content, and object identity. Payment evidence is PMCM-only; signed storage URLs must match the configured project and exact object path.

### Removed

- Broad sample API routes and browser-local demo fallbacks are retired. Guarded local fixture seeding remains available.
- Unused API ports, DTOs, portal primitives, package dependencies, and UI exports were removed without changing supported user workflows.
