# P.R.I.S.M feature ledger

## At a glance

- **Purpose:** Record the active product decision for each feature family and candidate.
- **Authority:** Normative product decision register; implementation work must not silently change a row.
- **Scope:** Feature intent, current state, decision, ownership, dependencies, permissions, evidence, and UX surface.
- **Use when:** Adding, revising, merging, splitting, deferring, gating, or retiring feature scope.
- **Change when:** Product intent, system goal, lifecycle placement, dependency, permission boundary, or completion evidence changes.
- **Verify with:** The current product model, readiness gates in evolution governance, architecture, and affected app/API checks.

This ledger is the product decision layer for feature work. It does not replace
the source-preserving catalog. It decides how catalog features and redesign
candidates should move forward.

## Selected client and supplier delivery

The [client and supplier workflow contract](client-supplier-workflows.md) records the selected FL-002, FL-004, FL-005, FL-006/024, FL-007, FL-010, FL-011, and closure slices: versioned signing and files, briefing submission, official-layout decisions and annotations, venue/styling decisions, closeout and consent moderation, supplier contract corrections, schedules, creative tasks, and an actual payable release ledger. These slices do not mark the broader feature families complete or activate external services.

## Decision Legend

| Decision | Meaning |
| --- | --- |
| Keep | Implement or harden mostly as described. |
| Revise | Keep the intent but change UX, data, workflow, boundaries, or wording. |
| Merge | Fold multiple catalog items into a stronger workflow. |
| Split | Break an oversized feature into smaller implementation slices. |
| Add | New feature should enter scope because it improves P.R.I.S.M. |
| Defer | Valid feature, but not needed until a later maturity stage. |
| Retire | Remove from active scope; keep traceability. |
| Gate | Allow only after a prerequisite is complete. |

## Correctness and policy evidence

The following notes distinguish bounded correctness fixes from full feature
completion. They do not promote a whole feature family from partial to complete.

- **FL-002/FL-010:** Signed conforme no longer fabricates approved billing. Client payment totals reconcile actual paid and outstanding amounts.
- **FL-005:** Proposal decisions require the primary client's verified identity and an issued proposal version. Reasons, actor/version identity and retries are durable. PMCM issues proposals from the selected event's commercial proposal panel: the cost estimate and a numbered version are created together with the issued proposal document the client reviews (with a one-page PDF copy stored as an event deliverable), and the client sees only the title, summary and total. After the client approves, a new version is refused; scope changes go through the change register. The client approve/request-revision surface caps revisions at 3. Live PostgreSQL and browser acceptance of the full journey are still open; CE builder depth, Canva/Zoom, and AI drafts stay gated.
- **FL-007/New-S5:** Closure review prompts are event-scoped to confirmed supplier assignments. Reviews are advisory, not an archive gate, and ratings, dimensions, and notes remain PMCM-only.
- **FL-007:** Supplier terminal transitions, selected-assignment confirmation, cancellation and event-review retries enforce state, identity and transactional audit rules. Approved applications create a pending-first-event supplier with a conversion audit, and each event allows one PMCM assessment per supplier. PMCM has a paged supplier directory and profile with private ratings, scorecards, certification status, recent review/reliability/certification records, and event engagement facts. Supplier routes remain scoped away from PMCM-only review data. Live PostgreSQL and browser acceptance are still open; broader reliability analytics remain future work.
- **FL-008:** Active assignment identity controls coordinator scope and availability. Same-date booking and replacement share a database lock. Namesakes do not grant authority.
- **FL-010:** Billing correction approval requires a different PMCM user than the requester (403 on self-approval, nothing written); the requester may still reject (withdraw) their own pending correction. Identity is the verified actor id stored in `requested_by_id`; legacy rows without an id fall back to the requester name. Waivers and additional billing stay single-step. The PMCM billing panel disables Approve on the viewer's own requests.
- **FL-013:** Closeout uses explicit deliverables, billing, logistics, unresolved issues and client feedback. Logistics passes only with a PMCM-recorded, audited logistics completion record (replacement requires a correction reason; notes stay PMCM-only); an archive override needs a durable PMCM reason.
- **FL-015:** Sensitive routes require verified sessions and role/event ownership. Supported operational deletion redacts identity copies atomically; PMCM-executed access/export returns a subject-scoped bundle, and native client/supplier/account erasure and validated name/email correction are executed atomically through PMCM privacy operations. Event-scoped guest name/email correction is implemented with legal-hold and destination-name collision checks. Guest deletion requires a unique roster identity and updates only that roster and its linked check-ins; ambiguous identities and name-only feedback require individual record review. Live AI remains disabled before any provider call.
- **Authority and lifecycle policy:** The [accepted authority/lifecycle policy](event-authority-and-lifecycle-policy.md) is implemented: PMCM-designated, revocable and audited Event Day System Operator authority over other coordinators' attendance; a seven-day guest-feedback window anchored to the recorded actual event end, open after archive, with check-in still closed for archived events; and the four catalog client categories with legacy Private written as Individual by a data migration. School and Other remain historical values.

## Accepted staffing policy

- New staffing-role writes use the catalog in `packages/types/src/schemas/coordinator-roles.ts`: General Coordinator, Event Day System Operator, Registration Staff, Floor Director, Stage Director, Ingress and Egress Assistant, Usher. Historical unknown strings remain readable and are not rewritten. Operator actions still require event-specific designation; the role label does not grant authority.
- Skill requirements are advisory. Explicit desk filters require every selected skill. The API preserves activity, role, date-conflict and declared-availability eligibility; normalizes tags; ranks required-skill overlap before deterministic name/ID ties; then caps suggestions at five. Match/missing details explain the result. This supports FL-008/FL-023 without claiming a full staffing heatmap.
- Reassignment approval remains manual. The stored two-minute deadline is not an approval trigger. Acknowledgment follow-ups use the configurable seven-day default; the supplier ingress sweep uses the fifteen-minute late threshold. Notification queue evidence does not establish external delivery.
- Archived coordinator events remain selectable for scoped historical reads. Portal action controls and coordinator event-day, schedule, handoff, report, acknowledgment and withdrawal API writes enforce read-only archive access; switching to a current event restores normal actions.
- Registration staff need an active assignment to the event. Archived roster reads remain available, while verification, walk-in creation and check-in reject archived events; verification checks archive status under the event lock.
