Date: 2026-06-20
Branch: `plan/remediation-calendar-system`
Related plan: `docs/superpowers/plans/2026-06-15-prism-redesign-agile-calendar.md`

This review checks the July sprint plan against the full P.R.I.S.M system goal, the v4 feature ledger, the implemented-feature reality, and the current app/package layout. It is not a replacement for the feature ledger. It is the missing-work audit that tells each owner what must be true before the system can be called complete enough for the July 31 demo and defense story.

## Full System Goal

P.R.I.S.M should operate PMCM's internal event lifecycle from inquiry to closure without collapsing the role apps into one generic dashboard. The complete system is not measured by every catalog item being production-grade. It is measured by whether each lifecycle step has a working role-safe slice, a documented gate, or a named post-July owner.

| Goal area | Complete-system expectation | Current risk | Required completion rule |
| --- | --- | --- | --- |
| Lifecycle continuity | Inquiry -> accepted inquiry -> signed conforme -> planning -> event day -> closeout/archive can be demonstrated as one coherent story. | Existing flows are split across many routes and some rely on fallback/sample state. | Sprint 4 demo path must name route, actor, data contract, command output, screenshot, and known gates for each lifecycle step. |
| Role boundaries | PMCM/coordinator use `apps/event`; client uses `apps/client`; supplier uses `apps/supplier`; guest uses `apps/guest`; all share `apps/api`. | Some UI still derives data from broad compatibility paths or large page-owned state. | No new feature can close unless its normal path uses scoped API/types or the docs explicitly mark it as compatibility-only. |
| Trust and evidence | Permissions, audit, notification intent, file visibility, lifecycle gates, and failure states are visible and testable. | Several features are visually present but not fully backed by production adapters, storage, or external auth. | Each feature family must close as delivered, thin delivered, gated, deferred, or post-July with evidence. |
| Operational usefulness | Ms. Mys and PMCM can see what needs attention, who owns it, what is blocked, and what changed. | The plan has owner tasks, but not every feature has a current-vs-target decision. | The feature completion review below becomes the task source when sprint tasks are missing. |

## Plan Amendments From This Review

1. The July plan should not say a feature is complete when it only has a visible UI. Completion requires contract/source, permission boundary, failure state, and evidence.
2. Sprint 3 should force explicit non-work: any PMCM depth slice not chosen by Francis becomes gated/post-July immediately.
3. Sprint 4 should include a closeout matrix for every FL row, not just broad acceptance criteria.
4. New features are allowed as candidates, but July work should prioritize evidence, boundaries, and lifecycle continuity over expansion.
5. Every route that still uses compatibility data should name the compatibility owner and the condition for removal.
