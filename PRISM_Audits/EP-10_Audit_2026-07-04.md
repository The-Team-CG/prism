## Executive summary

**EP-10-S01 has a real, working backend contract that is more solid than the tracker's 50% suggests, but the tracker's own note about lingering fallback logic is confirmed correct, and is more dangerous than "some UI code the AC doesn't like."** `EventReadModelsService.clientActionCenter()` is a genuine, well-scoped read model — `resolveActor` → `requireActorRole([Client])` → `visibleEventsForActor` (which itself only returns events where `clientPortalStatus === 'unlocked'`, i.e. conforme signed) → aggregation from seven client-safe source tables (briefings, documents, floor plan drafts, billing statements, payment milestones/records, post-event documents). No coordinator names, no supplier data, no CE-rule detail anywhere in its output — confirmed clean against FR-33. But `apps/client/src/app/components/dashboard/Dashboard.tsx` still carries a full parallel fallback derivation function (`getClientDashboardActions`) that is not just present but **actively invoked whenever the contract fetch fails** — and that failure is caught silently (`.catch(() => setActionCenter(null))` in `use-client-dashboard-state.ts`) with no error surfaced to the client. The practical effect: if the action-center API call fails for any reason, the client silently sees a narrower, locally-computed action list instead of an error state, and backend-only signals (a `critical`-priority overdue payment, a `rejected` document) can disappear from view with nothing telling the client anything is wrong. This is a more serious version of the "fallback logic remains" gap than a simple AC checkbox miss.

**EP-10-S02 is close to genuinely 0%, with a caveat: don't credit unrelated fragments to this story.** No "timeline" route, nav item, or CL2 toggle exists anywhere in the repo (`apps/client`, `apps/api`, or `packages`) — confirmed by repeated repo-wide search. Two small, pre-existing UI fragments happen to overlap thematically: a six-step "lifecycle strip" widget in the dashboard header (`dashboard-tabs.tsx`) showing coarse done/pending states for six phases (no dates), and a `schedule` route (`Dashboard.tsx` `renderSchedulePage`) showing the event date plus payment due dates only — 2 of the 5 dates the AC requires (missing conforme date, proposal acceptance date, floor plan approval date as distinct timeline entries). Neither is S02's own feature; both are pieces of S01's dashboard/billing surface that happened to exist first. The CL2 per-event toggle and the event-day view it's supposed to gate do not exist in any form.

**EP-10-S03 is a confirmed second negative control for this initiative (the first was EP-07 Chain B) — genuinely, exhaustively absent, not a "different feature under the same name."** Repo-wide search for `ocular`, `site visit`, `venue visit`, `walkthrough`, `inspection`, `ChangeTask`/`change-task` found zero implementation matches in any `.ts`/`.tsx` file under `apps/` or `packages/` (only doc/handoff mentions). `FloorPlanWorkflowService.createFloorPlanDraft` (`floor-plan-workflow.service.ts:57-126`) has exactly one precondition — `requireEvent(eventId)` — and the generic command runner it uses (`WorkflowCommandService.execute`) has no hidden hooks that could smuggle in a gate. **This directly and concretely corrects PA-59's working assumption**: the assumption was "an override path probably exists for the ocular gate, mechanism unconfirmed." The actual code has no gate at all, on either side — nothing to override, because nothing enforces the precondition in the first place.

**New finding — PA-186 (HIGH):** The AC's "no fallback derivation logic remaining" requirement is not met, and the failure mode is worse than a leftover code path: `getClientDashboardActions` (`Dashboard.tsx:345-420`) is live-merged with contract data on every render (`Dashboard.tsx:889-901`), and silently becomes the *entire* rendered list whenever the action-center fetch fails, because that failure is swallowed with no user-facing error (`use-client-dashboard-state.ts:148-152`, `:159-167`, both `.catch(() => setActionCenter(null))`/`.catch(() => null)` with no `setError` call). The fallback list has no concept of the contract's `critical`/`rejected` signals, so a real overdue-payment or rejected-document item can vanish from the client's view with no indication anything failed.

**New finding — PA-187 (MEDIUM):** False-failure UX on successful writes, traced via `ecc:silent-failure-hunter`. `submitPreference` (`Dashboard.tsx:849-877`) and the editor-draft creation path (`Dashboard.tsx:815-847`) both call `await refresh()` immediately after a successful `createFloorPlanPreference`/draft-creation write. `refresh()`'s `loadClientState` call is unguarded (only the action-center half is caught) — if that GET fails post-write, the surrounding `try/catch` reports `"Unable to submit layout preference"` / `"Unable to open layout view"` even though the write already committed server-side (audit log + notification queued, `floor-plan-workflow.service.ts:202-207`). A client seeing this message has a real reason to believe the action failed and may resubmit. Root cause one level deeper: `WorkflowCommandService.execute` (`workflow-command.service.ts:31-35`) runs `sideEffects` (audit/notification) with no try/catch after the DB transaction commits — a side-effect failure there also surfaces as a full request failure indistinguishable from a real write failure, with no compensating "write succeeded, side effect failed" log for an operator to find later.

**New finding — PA-188 (LOW):** `apps/client/src/lib/prism-api.ts:872-901` bundles dead mock-mode functions (`assignCoordinator`, `acknowledgeCoordinator`) that hardcode a PMCM coordinator identity ("Marco Santos"). Never invoked by any component in `apps/client` (confirmed by repo-scoped search) — not a live leak, but it means PMCM-actor mock data ships inside the client-facing app's own bundle for no functional reason. Likely copy-pasted from a shared API-client scaffold with `apps/event`. Hygiene-only; not a FR-33 breach since unreachable.

**New finding — PA-189 (MEDIUM):** AC-5's "real-time... reflection" is not implemented as real-time. `use-client-dashboard-state.ts` uses a flat 30-second cache TTL checked only at mount/navigation (`CLIENT_STATE_CACHE_MS`, no `setInterval`/polling/WebSocket anywhere in `apps/client`). A client who stays on one page will not see a PMCM-side change until they navigate away and back, or manually trigger a refresh-causing action.

**Completion estimate: ~60%.** The backend contract itself is well-built, correctly role-gated, correctly conforme-gated, and clean of PMCM-internal data — genuinely ahead of "50% In Progress" on that axis. But the frontend gap is not the AC's literal "fallback exists" checkbox so much as a masking bug: real backend signals can silently disappear behind a narrower fallback with no error surfaced, which is a materially worse client-trust problem than "some old code wasn't deleted yet."
