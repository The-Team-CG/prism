## Executive summary

**EP-09-S01 is a "different feature under the same name" case, the same pattern as EP-06-S02/defenseReadiness.** A `FileRequirementsMatrixService`, `FILE_REQUIREMENT_READER`/`FILE_REQUIREMENT_COMMANDS` tokens, and a controller all exist — strong surface signals this story is built. But what they actually implement is a **read-only, hardcoded closure-readiness dashboard** (6 fixed item types — signed conforme, post-event documents, billing statement, floorplan, supplier reviews, client feedback — each computed from other modules' existing data) with **zero create/update/delete capability**. `FILE_REQUIREMENT_COMMANDS` is bound to a static config object (`{ storageProviderMode: 'metadata_only' }`), not a service — there is categorically no way for a PMCM Admin to define a custom file requirement with a document name, type, due date, or submitter role. The AC as written describes a configurable requirements system; the code implements a fixed status board that happens to share a name and DI tokens with it.

**EP-09-S02's core validation logic is real, well-built, and genuinely reachable in production** — just not through any endpoint file-ops itself owns. `DocumentVaultService.validateUploadMetadata` (extension+size validation, UUID-randomized filenames, original filename kept as metadata only) is consumed by `supplier-ops` (contract uploads, event-day status photos, both audited in EP-07 Chain A) and `guest-ops` (feedback photo/video uploads) via `useExisting` DI bindings. The signed-upload-URL factory correctly throws `ServiceUnavailableException` unconditionally — this is a deliberate, working "unavailable until a real storage adapter is approved" gate, matching the AC exactly, not an accidental stub. But: there is no PMCM-Admin-facing or dedicated document-vault upload endpoint anywhere, and the MIME check itself is extension-plus-client-supplied-string only, not real content detection — a genuine FAIL against "actual detection, not extension-only."

**The S01↔S02 dependency the tracker implies does not exist in the code.** No `OpsDocument` field references a file-requirement ID (confirmed against the Prisma schema), and S01 has no real requirement records to link to in the first place. The matrix's "status" per item is inferred by loose heuristics (e.g., `document.type.toLowerCase().includes('conforme')`), not a hard foreign-key relationship. The two stories are functionally independent — not because either was deliberately built standalone, but because the connecting mechanism (a real requirement record with an ID) was never built.

## EP-09-S01 — File Requirements Matrix

**Tracker:** To Do, 0%, C2 — **not accepted without a search, per the brief; searched, found a different feature under the same name.**

| AC | Verdict | Evidence |
|---|---|---|
| PMCM Admin can define a file requirement per event: name, type, due date, submitter role, visibility | **FAIL** | `FileRequirementsMatrixService` (`file-requirements-matrix.service.ts`) has exactly two public methods: `buildForEvent()` and `closeGates()`, both read-only. The six "requirement" items (`itemsForEvent()`, lines 94-165) are hardcoded object literals with fixed `key`/`label`/`ownerRole`/`visibleToRoles` — there is no `createRequirement`, `updateRequirement`, or any method that accepts admin-supplied name/type/due-date/submitter-role input. Nothing in this service, its controller, or its DTO (`file-requirements.dto.ts`, which only defines an actor-context DTO for the GET request) creates a requirement record of any kind. |
| Metadata-only gate enforced, no real file storage in this story's scope | **PASS, trivially** | This service performs zero file storage of any kind — it only reads existing `OpsDocument`/`OpsBillingStatement`/`OpsPaymentMilestone`/`OpsSupplierReview` rows created by other modules. There is no upload path in this story's own code to evaluate. |
| **FILE_REQUIREMENT_READER for reads, FILE_REQUIREMENT_COMMANDS for writes, no direct Prisma bypass** | **FAIL on both counts** | `FILE_REQUIREMENT_READER` is bound (`file-ops.module.ts:19`, `useExisting: FileRequirementsMatrixService`) but its own controller (`event-file-requirements.controller.ts:10`) injects the **concrete class directly**, not `@Inject(FILE_REQUIREMENT_READER)` — the port is bound in DI but never consumed through the token, the same "bound is not reachable" pattern as EP-08's `BILLING_READER`/`PAYMENT_STATUS_READER` (PA-179). `FILE_REQUIREMENT_COMMANDS` is worse: it's bound via `useValue: { storageProviderMode: 'metadata_only' }` (`file-ops.module.ts:10,20`) — a **static config object, not a service** — and its own port interface (`file-requirement-commands.port.ts`) declares zero methods. There is no "writes" side to check because nothing implements one. |
| PMCM-internal requirements not exposed to client/supplier submitter views | **PASS, for what exists** | The controller filters `matrix.items` by `item.visibleToRoles.includes(actor.role)` (`event-file-requirements.controller.ts:26`) after `requireCanReadEvent` scopes the actor to their own visible events. `supplier_reviews` is hardcoded `visibleToRoles: ['pmcm-admin']` only — correctly excluded from client/supplier. This filtering logic is real and works, just applied to fixed items rather than admin-defined ones. |
| PMCM Admin can update/remove a requirement before due date, reflected immediately | **FAIL** | No update/remove capability exists at all (see above); there are no due dates on any item either — `dueDate?: string` exists in the type shape but is never populated by `itemsForEvent()` for any of the six hardcoded items. |
| Supplier/client can only view their own assigned requirements | **N/A — no per-actor assignment exists** | Visibility is role-level (`visibleToRoles` per item type), not per-supplier or per-client instance-level, because there's no concept of "assigning" a requirement to a specific submitter in the first place. |

**New finding — PA-182 (HIGH):** EP-09-S01 as described in its own AC (an admin-configurable file-requirement definition system with CRUD, due dates, and submitter-role assignment) does not exist. What exists under the same service name and DI tokens is a different, already-built feature: a read-only, hardcoded event-closure-readiness dashboard that infers six fixed status items from other modules' existing data. This is the same "same name, different feature" pattern already documented for EP-06-S02/defenseReadiness — worth reading this story's Done/To-Do status with that precedent in mind.

**New finding — PA-183 (MEDIUM):** Even the read-only matrix that does exist has no frontend consumer. `prismApi.fileRequirements()` (`apps/event/src/lib/prism-api.ts:707-708`) is defined and typed, but a repo-wide grep for any call to it (`prismApi.fileRequirements` or `.fileRequirements(`) finds only its own definition — no component in `apps/event` ever invokes it. Dead client code, same pattern as EP-01's `logInquiryOnBehalf`.

**Completion estimate: ~10%.** The role-filtering and event-scoping logic that does exist is correctly written and reuses already-audited access-control patterns soundly — but the feature the AC describes (configurable requirements with CRUD) is entirely absent, and the read-only feature that substitutes for it isn't even wired to a UI.

## EP-09-S02 — Document Vault Upload with MIME Validation

**Tracker:** To Do, 0%, C3 — **not accepted without a search, per the brief; searched, and the core engine is real, just not dedicated to this story.**

| AC | Verdict | Evidence |
|---|---|---|
| PMCM Admin and Supplier can upload documents from their respective portals | **PARTIAL** | No PMCM-Admin-facing or file-ops-owned upload endpoint exists anywhere. Supplier-side upload is real but narrow: `SupplierNetworkWorkflowService.uploadSupplierContract` (audited in EP-07 Chain A) and the event-day status photo upload both call `DocumentVaultService.validateUploadMetadata` via the `SUPPLIER_DOCUMENT_VAULT` token (`supplier-ops.module.ts:56`, `useExisting: DocumentVaultService`) — but these are narrow, purpose-specific upload paths (a contract, a status photo), not a general-purpose "upload any document" flow for either role. |
| **Upload processed through DocumentVaultService; MIME validation is real detection, not extension-only** | **PARTIAL — service usage PASS, detection method FAILS** | `validateUploadMetadata()` (`document-vault.service.ts:38-56`) genuinely is the shared validation path — confirmed used by `supplier-ops` and `guest-ops` (`guest-workflow.service.ts:41,144-145,261-264`), not dead code. But the check itself only compares a **client-supplied `mimeType` string** and the filename extension against a static allow-list (`ALLOWED_UPLOAD_TYPES`, lines 26-34) — no file content/magic-byte inspection occurs anywhere, and the function signature itself never receives a file buffer, only `fileName`/`mimeType`/`sizeBytes` metadata. A forged `mimeType: 'application/pdf'` header on a file named `x.pdf` containing arbitrary bytes passes validation untouched. This is extension+client-header trust, not "actual detection." PA-184. |
| Exactly seven accepted file types: PDF, DOCX, XLSX, JPG, PNG, MP4, MOV | **PASS** | `ALLOWED_UPLOAD_TYPES` (lines 26-34) has exactly these 7 entries (JPG covers `jpg`/`jpeg` extensions under one MIME type) |
| Files stored with randomized filenames, original retained as metadata only | **PASS, traced through the actual write path** | Line 57: `generatedFileName = `${randomUUID()}.${extension}``; `storageKey` (line 65) is built only from a caller-supplied prefix plus this generated name, never from user input directly; `originalFileName` (line 60) is stripped of path components and returned as a separate metadata field, never used in the storage key |
| Signed upload URLs return a clear unavailable state until a real storage adapter is approved | **PASS, exactly matches the described gate** | `MetadataOnlySignedUploadUrlFactory.createSignedUploadUrl()` (`signed-upload-url-factory.port.ts:22-26`) unconditionally throws `ServiceUnavailableException('Signed upload URLs require an approved storage adapter')`, confirmed by its own test asserting the rejection. This is a deliberate, correctly-implemented "not yet available" state — not an accidental stub or a silently-broken feature. |
| Each document associated with event, submitter identity, timestamp, and the file requirement it satisfies | **PARTIAL — three of four; the fourth doesn't exist to link to** | `OpsDocument` (schema, `event_core` schema block) has `eventId`, `uploadedByRole`, `uploadedAt` — event/submitter-role/timestamp are all real fields. There is **no field referencing a file requirement** anywhere on this model, confirmed against the full schema. This isn't a broken link so much as there being nothing on the other end to link to, since S01 has no real requirement records (see above). PA-185. |
| PMCM Admin views all documents per event; Supplier views own/shared only | **Not independently evaluable** | No dedicated document-listing endpoint for this story was found; existing document reads (e.g., `pmcmEventWorkspace`, audited in earlier epics) are PmcmAdmin/System-gated generally, consistent with but not specific to this AC |
| Client/guest cannot upload/read unless granted via the file requirement's visibility setting | **N/A** | Since no file requirement with a per-instance visibility setting exists, this conditional-access mechanism has nothing to condition on |

**Completion estimate: ~40%.** The validation engine itself — type/size checking, filename randomization, the deliberate signed-URL "unavailable" gate — is genuinely solid, tested, and already load-bearing for two other real features (supplier contract/status uploads, guest feedback uploads). What's missing is a dedicated general-purpose upload surface for this story specifically, true content-based MIME detection, and anything to link an upload back to a requirement (because nothing exists on the requirement side to link to).

## Cross-cutting: resolveActor sweep

`event-file-requirements.controller.ts`'s single endpoint calls `resolveActor` then `requireCanReadEvent(actor, event, ...)` before returning any data (lines 17-21) — consistent with the guarded pattern found in every module checked this initiative (EP-05/EP-06 exploitable, every EP-07 module and EP-08's finance-ops guarded). This is a fifth confirmed instance of the module being present-and-guarded, not a new exploitable instance.

## Cross-cutting: the S01↔S02 connection, traced explicitly

Traced per the brief's instruction rather than assumed. There is no code path where an uploaded document (via `supplier-ops`/`guest-ops`, the only real upload consumers of `DocumentVaultService`) references a file-requirement ID, and no code path where `FileRequirementsMatrixService` reads anything resembling a requirement-to-document foreign key — its `itemsForEvent()` matches documents to matrix items by loose string heuristics (`document.type.toLowerCase().includes('conforme')`, `.includes('feedback')`), not a relational link. **The two stories are functionally independent in the running system today** — not because they were each deliberately scoped standalone, but because the AC-implied connecting mechanism (a real, creatable file requirement with an ID that an upload could reference) doesn't exist on the S01 side for anything to link to.

## Cross-cutting: EP-15-S03 MIME validation, reusable piece confirmed to exist

Per the brief's instruction to check whether EP-15-S03's MIME validation exists anywhere as reusable code even while tracked 0%: **it does** — `DocumentVaultService.validateUploadMetadata()` is exactly this reusable piece, and it is genuinely shared across `file-ops` (its own definition), `supplier-ops`, and `guest-ops`. This is the same situation already noted for `uploadConforme` in the EP-04/EP-08 audits: that flow does its **own separate inline** PDF-only check rather than calling this shared service — now confirmed as a third instance of the same inline-vs-shared duplication pattern (uploadConforme's inline check, DocumentVaultService's shared check used by 2 modules, and no unification between them). Not raising a new PA for this — it's a consistency/DRY observation, not a security or correctness defect, since both paths do enforce *some* type restriction.

## Silent-failure findings (via `ecc:silent-failure-hunter` subagent, EP-09 file-ops surface)

No swallowed-error or empty-catch-block findings — there are no `try/catch` blocks anywhere in file-ops; errors propagate as unhandled Nest exceptions (`BadRequestException`, `NotFoundException`, `ServiceUnavailableException`), and the write-then-unguarded-audit pattern already logged elsewhere (PA-166/172/180) does not apply here for a different reason than "guarded correctly" — **there is no write path in this module at all** to have a race with an audit call. The subagent independently reconfirmed the DI-token-bound-but-unreachable pattern (`FILE_REQUIREMENT_READER`/`FILE_REQUIREMENT_COMMANDS`/`SIGNED_UPLOAD_URL_FACTORY`, zero `@Inject` consumers anywhere), matching the same shape as EP-08's PA-179.
