## Standing check — auth-gap sweep (5th–6th instances found, different shape than EP-01–EP-04)

Unlike EP-01 through EP-04, **the floorplan module's own controller is correctly gated.** All four write endpoints in `apps/api/libs/modules/floorplan/src/controllers/event-floorplans.controller.ts` call `requireCanMutateOfficialFloorplan` or `requireActorRole` and await them (lines 29, 44-49, 69, 84). This breaks the EP-01–EP-04 pattern in a good way and is worth stating plainly rather than assuming the pattern repeats everywhere.

**However**, the canvas editor that PMCM Admin (and, per the click-path trace, the client) actually uses to persist floor plan content does **not** go through that controller — it goes through a separate, parallel module: `apps/api/libs/modules/plans/`. That module's controller (`plans.controller.ts:10-18`) resolves **no actor at all** on `GET :planId`, and its `PUT :planId` passes a raw, unvalidated `actor: Record<string, string>` straight to `PlansService.updatePlan`, whose `assertCanUpdatePlan` (`plans.service.ts:157-180`) is fail-open by construction:

```ts
const role = (actor.actorRole ?? actor.role ?? 'pmcm-admin').trim().toLowerCase();
if (role !== 'client') return;   // anything that isn't literally 'client' is allowed through, unrestricted
```

A missing actor role defaults to `'pmcm-admin'` (fully trusted); any role string other than the exact literal `'client'` (supplier, coordinator, guest, a typo, garbage) short-circuits to `return` with no further checks — including the "approved plans are read-only" check, which only executes inside the `client` branch. `GET :planId` (`plans.service.ts:61-72`) has an unused `_actor` parameter and zero access control of any kind.

This is confirmed on **both** `main` and the `feature/ep-05-s04-ac-5-role-guards` PR branch — the AC-5 role-guard work added three real UI-layer guards in `apps/event` but did not touch `plans.service.ts` at all.

## Cross-story dependency check — EP-05-S01 conforme gate vs. EP-04-S01's storage stub

**Resolved: no dependency, because no explicit gate exists to depend on anything.** `FloorPlanWorkflowService.createFloorPlanDraft`'s `validateState` (`floor-plan-workflow.service.ts:66-68`) only calls `requireEvent(eventId)` — it never reads `OpsEvent.conformeSignedAt` or any conforme-related field. The only real-world barrier is incidental: an `OpsEvent` row does not exist until `uploadConforme` creates one (established in the EP-04 audit), so PMCM Admin cannot select an event to attach a draft to before conforme is uploaded. That incidental gate depends only on the `OpsEvent` row's **existence**, which `uploadConforme` creates from `input.fileName`/`mimeType`/`sizeBytes` metadata alone — it does **not** depend on the actual PDF bytes EP-04-S01 never stores. So EP-04-S01's storage stub does not block this incidental gate. But it compounds a separate problem already on record from the EP-04 audit (PA-139, no server-side PDF format validation): a fake metadata-only "conforme upload" with no real signed document is sufficient to unlock floor plan creation, and neither EP-04 nor EP-05 has any check that would catch it.
