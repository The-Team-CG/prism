## EP-18-S01 — Consistent Design System Across All Five Portals

**Tracker claim:** In Progress, 50%, Owner Maxine, no dependency.

**Verified directly:**

1. `packages/ui` contains a real, substantial component library: `PrismButton`, `PrismBadge`,
   `PrismCard`/`PrismCardHeader`/`PrismCardContent`, `PrismAppShell`, `PrismDashboardShell`,
   `PrismPublicShell`, `PrismTopBar`, `MobileActionDock`, `RolePageHeader`, and more — not a
   stub. This is real progress the tracker's 50% is at least partly crediting.
2. **All five portals do consume `@prism/ui` at their top-level entry points** —
   `apps/event/src/app/page.tsx`, `apps/event/.../dashboard/EventDashboardClient.tsx`,
   `apps/client/.../dashboard/Dashboard.tsx`, `apps/client/.../public-inquiry/PublicInquiryPage.tsx`
   (the fifth "portal," the public inquiry surface, lives as a route inside `apps/client` rather
   than as a separate Next.js app — confirmed by direct file read, not a separate deployable),
   `apps/supplier/.../dashboard/page.tsx`, `apps/guest/.../dashboard/page.tsx` all import from
   `@prism/ui`.
3. **AC3 ("app-local duplicates removed") is not met.** Every one of the four Next.js portal
   apps (`event`, `client`, `supplier`, `guest`) still maintains its own local
   `src/app/components/ui/` primitive layer alongside `@prism/ui`. Confirmed directly:
   `apps/event/src/app/components/ui/button.tsx` is a near-identical, independently duplicated
   `cva`-based Button implementation (same six variants, same four sizes) sitting next to
   `packages/ui`'s own, differently-named `PrismButton`. Within `apps/event` alone, **14 files
   still import the local `./button`, versus 6 files importing `@prism/ui`** — the app-local
   duplicate is used more than the shared primitive in this app today. `apps/client` maintains
   its own local `calendar.tsx`, `alert-dialog.tsx`, `pagination.tsx`, `carousel.tsx`,
   `sidebar.tsx` alongside 5 files that do use `@prism/ui`. This is real, current, widespread
   duplication, not a stale finding.
4. **No route-review log exists anywhere in the repo.** A repo-wide search for "Maxine" and
   "route-review" in real files returns nothing outside documentation and the coincidental test
   fixture noted above. AC5 is a clean binary check and it fails cleanly: absent, not partial.
5. Visual consistency (AC4) cannot be confirmed as achieved: given the widespread coexistence of
   app-local component duplicates with different variant systems from `@prism/ui`'s own
   primitives, some divergence across portals is the more likely state, though this audit did
   not drive a live browser comparison across all five portals to confirm every element
   individually — stated plainly per this initiative's verification standard, this is a
   file-inspection-based conclusion, not a pixel-level visual regression check.

**Real completion: ~35-40%, not 50%.** Direction: **the tracker's 50% is a mild over-claim.**
Real, substantial shared-component infrastructure exists and is genuinely adopted at the
entry-point level (crediting real progress), but two of the AC's requirements are clean binary
failures with zero partial credit possible (no route-review log at all), and the "duplicates
removed" requirement is actively contradicted by current, heavier-than-shared usage of
app-local components in at least one portal. Recorded as **PA-251** (token system reconfirmed
unchanged) and **PA-252** (app-local duplication confirmed real and widespread).

## EP-18-S02 — Shared Route Inventory and Navigation Shell

**Tracker claim:** To Do, 0%, Owner Maxine, dependency EP-18-S01.

**Verified directly:**

1. **No route inventory document exists anywhere in the repo**, in any format (confirmed by a
   direct glob search for `route-inventory*` and by the same repo-wide search that found no
   route-review log). AC1 is a clean binary check and it fails cleanly.
2. **A real navigation shell does exist in `packages/ui`, and it is not "in name only."**
   `app-shell.tsx` (1,071 lines) implements `PrismAppShell`: a responsive sidebar (collapsible,
   searchable, grouped by section), a primary icon rail, a mobile navigation drawer with its own
   open/close state, a top bar with search/account-menu/notifications, and a mobile action dock
   — all genuinely built, not scaffolding. `dashboard-shell.tsx` wraps it as `PrismDashboardShell`
   for direct reuse. This **is** confirmed, directly, to be consumed by all portals checked:
   `apps/supplier/.../dashboard/page.tsx`, `apps/guest/.../dashboard/page.tsx`,
   `apps/event/src/app/page.tsx`, `apps/event/.../EventDashboardClient.tsx`,
   `apps/event/.../coordinator-view.tsx`, `apps/client/.../dashboard/Dashboard.tsx`. This is a
   genuine positive finding this audit did not expect given the tracker's 0% claim, and it does
   not appear to be a "different feature under the same name" — it is exactly the navigation
   shell the AC describes, and it does not duplicate itself per portal.
3. Mobile/desktop breakpoint handling (AC6): confirmed present in the component's own Tailwind
   classes (`md:flex`, `md:hidden`, `md:pl-[...]`, a separate mobile drawer state) — this is a
   real, built responsive implementation, not asserted only by the AC description.
4. Cross-portal navigation not exposing unauthorized routes (AC3): the shell component itself
   takes `navItems` as a prop and contains no role-authorization logic of its own — it renders
   whatever list a given portal's page passes in. This is architecturally sound for the actual
   deployment shape (four separately-deployed Next.js apps, not one shared route table), which
   sidesteps the literal cross-portal-leak risk the AC describes by construction rather than by
   an access check that could be misconfigured. No new resolveActor-relevant finding here.
5. No route-review log entry confirming shell application per portal (AC5): absent, same clean
   binary failure as S01's AC5, since this is the same log across both stories.

**Real completion: ~30%, not 0%.** Direction: **the tracker's 0% clearly under-claims**, in the
same direction as EP-17 but far less dramatically. This story's actual technical deliverable,
the navigation shell, is real, working, and already adopted by every portal checked — a
materially different picture from a story that has not been started. What is genuinely missing
is the documentation and audit-trail side of the AC (the route inventory and the route-review
log), not the shell itself. **This story's dependency on S01 does not appear to have been a
real blocker in practice** — the shell was built and adopted before S01's own token-migration
work reached anywhere near completion.
