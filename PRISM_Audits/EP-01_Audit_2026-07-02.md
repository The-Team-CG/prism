## EP-01-S03 — Client Onboarding Trigger (Owner D / Anthony)

**Tracker Claim:** Done, 100%. Gated on Approved status, creates client account, activates apps/client only, sends credentials/link, blocks non-PMCM, audit log with admin/timestamp/inquiry ID.

**Repo Reality:**
- No status literally called "Approved", code uses `'accepted'` (`inquiries.service.ts:226`, `schema.prisma`). Cosmetic naming discrepancy.
- Onboarding actually triggered by `uploadConforme()` (`inquiries.service.ts:208-437`), not a separate "onboarding" action. Correctly gates on `status === 'accepted'` (line 226), confirmed.
- No client account (`OpsUser`) created. Only creates/updates `OpsEvent` with `inquiryId` linkage (line 243), flips `clientPortalStatus: 'unlocked'` (lines 251, 302). Contradicts "creates a client account."
- "Activates apps/client only": only a boolean-ish flag set, no explicit app/port scoping logic in the API found.
- Credentials/activation link: only metadata fields set (`portalInvitationStatus/SentAt/ExpiresAt`) plus a generic notification. No token or activation-link generation found.
- **`uploadConforme` has no role/actor authorization check at all.** Controller route (`inquiries.controller.ts:58-61`) takes only `@Param` and `@Body`, no actor. `inquiry-workflow.service.ts:103-110` passes straight through with no `requireActorRole` call, unlike sibling endpoints (create, logOnBehalf, updateStatus) in the same file. "Blocks non-PMCM actors" AC is unmet at the server boundary for the endpoint that actually performs onboarding.
- Audit log write (`inquiries.service.ts:410-417`) records actor as hardcoded string `'PMCM Admin'`, not real identity, and captures `event.id`/`document.id`, not the inquiry ID. Contradicts AC requiring inquiry ID.

**Mismatch (substantial, tracker overclaiming):** No client account creation, no auth check on the triggering endpoint, no inquiry ID in audit log, no real activation-link generation, hardcoded admin identity in audit log.

**Extra, undocumented behavior:** `uploadConforme` also auto-generates a full billing statement (50/50 split), payment milestones, and post-event document placeholders (lines 256-403), significant business logic not mentioned in the S03 AC or tracker notes.

**Regression Check:** Status gating logic correctly rejects non-accepted inquiries. The bigger issue is the missing authorization boundary, a security-relevant gap regardless of when it was introduced.

## ADDENDUM, 2026-07-09

**What this corrects:** Adds one new PA finding (PA-275) surfaced during this session's EP-01-S02 "Log Inquiry on Behalf" frontend build-planning pass. Distinct from PA-258 (channel marking, reconfirmed in the 2026-07-05 addendum above) and distinct from the already-tracked `resolveActor` fail-open sweep (`ResolveActor_Sweep_2026-07-04.md`, 62 of 70 call sites). Does not change any percentage, qualitative verdict, or existing PA in this file.

**Why:** While planning the EP-01-S02 frontend build (session date 2026-07-09), fresh reads of `inquiries.controller.ts`, `inquiry-workflow.service.ts`, and `inquiries.service.ts` traced the full identity chain for `POST /api/inquiries/log-on-behalf` end to end, to confirm whether wiring in real session-derived identity (per the build plan) would genuinely satisfy the admin-identity AC. That trace surfaced a distinct authorization gap not previously logged as its own PA.

**Finding, confirmed via fresh same-session reads:**
- `inquiries.controller.ts:37-39` — `logOnBehalf(@Body() dto: CreateInquiryDto, @Query() actor: SampleActorDto)` passes the raw query-parsed actor DTO straight into `inquiryWorkflowService.logInquiryOnBehalf(dto, actor, ...)`. No `@UseGuards` decorator exists anywhere in this controller (confirmed: no `UseGuards` import in the file at all), for any route including this one.
- `inquiry-workflow.service.ts:84-91` — `logInquiryOnBehalf` is a pure passthrough: `context.inquiriesService.logInquiryOnBehalf(input, actorInput)`. Unlike its siblings in the same file, `listInquiries` (lines 46-48) and `listOnboarding` (lines 58-60), which both call `context.resolveActor(actorInput)` then `context.requireActorRole(...)`, this method calls neither.
- `inquiries.service.ts:91-106` — `const role = actorInput.actorRole ?? actorInput.role ?? OpsUserRole.Unknown;` is used directly for the `ForbiddenException` role-gate check (line 93) and directly assigned to the persisted `loggedByRole` (line 101); `loggedByName` (line 102) is taken directly from `actorInput.actorName`. Both values are exactly whatever the caller supplied in the query string, with no verification of any kind.

**Distinct from the existing `resolveActor` fail-open sweep:** that pattern is "calls `resolveActor()`, which defaults to `pmcm-admin` when nothing is supplied." This endpoint does not call `resolveActor()` at all, it reads the raw query DTO directly, with no resolution function in the loop at any point. Same family (unverified client-asserted identity), different mechanism, logged separately rather than folded into the sweep.

**Practical consequence:** Once EP-01-S02's UI ships, identity displayed and recorded through normal use of the app will be accurate, since the UI will always populate `actorName`/`actorEmail` from the real signed-in session. But the endpoint itself has zero server-side identity verification: any caller hitting `POST /api/inquiries/log-on-behalf?actorRole=pmcm-admin&actorName=<anything>&actorEmail=<anything>` directly, bypassing the UI, passes the PMCM-only role gate and can attribute an inquiry-log entry to any name of their choosing.

**PA-275 (HIGH, EP-01-S02):** `POST /api/inquiries/log-on-behalf` performs its PMCM-only role check and identity recording entirely from unverified, client-suppliable query parameters (`actorRole`, `actorName`, `actorEmail`), with no `resolveActor()` call, no guard decorator, and no server-side identity verification anywhere in the chain (`inquiries.controller.ts:37-39` → `inquiry-workflow.service.ts:84-91` → `inquiries.service.ts:91-106`). Severity assessed HIGH, not CRITICAL, by Francis: the mechanism (unverified, spoofable, client-supplied identity, zero verification) is the same shape as `uploadConforme` (PA-138/PA-259), which this initiative's EP-04 audit characterized as CRITICAL in prose narrative and an epic-level index tag (`_Audit_Index.md:9`), not a discrete per-PA severity field, but blast radius differs materially: `uploadConforme` unlocks the client portal, generates billing, and activates the event workspace in one transaction, while this endpoint's write stays contained to a single fabricated `OpsInquiry` record, with no billing, portal, or workspace side effects triggered on its own.

**Supersession note:** This does not change any existing verdict, percentage, or PA in this file or its 2026-07-05 addendum. PA-258 (channel marking) remains open and separate. EP-01-S02's frontend build (this session, 2026-07-09) addresses both PA-258 (adding a real `channel` field to the DTO/schema/service) and the admin-identity AC (wiring real session identity into the on-behalf call path only) in its implementation plan. PA-275 remains open as a distinct, unresolved authorization-boundary gap on the same endpoint, unaddressed by that build plan and requiring separate remediation.
