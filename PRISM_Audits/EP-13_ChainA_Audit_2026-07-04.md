**Explicit confirmation/retraction of the tracker's claim, as required:** the tracker's note — *"name-based check-in and walk-in flagging confirmed Partial per File 9. Remaining: headcount-only mode, walk-in policy enforcement, real-time count feed."* — **is CONFIRMED, not retracted, on every clause.** Name-based check-in and walk-in flagging are real, working, end-to-end, and backend-tested. Headcount-only mode and walk-in policy enforcement are genuinely absent, exactly as claimed. The one addition this audit makes beyond the tracker's own claim: the "real-time count feed" gap is architecturally different from what "Remaining" implies — the *data* already feeds both consumers correctly (S01, EP-12-S01); what's missing is push/poll refresh, not the feed itself (PA-189), plus a newly-found silent-staleness path on the PMCM side (PA-216).

**Working-UI-masking-broken-persistence check:** does NOT apply here — this is the rare case this initiative has been watching for where the opposite holds: the UI, the DTO validation, the service write, the Prisma commit, and a backend test all agree end to end. Worth recording as a second contrast case (after EP-10-S01) where "tracked as Partial" turned out to be an honest description, not an overstatement.

**New finding: PA-212 (MEDIUM).** The New-CL1 walk-in policy (private event + under 200 pax → automatic flag) has no server-side implementation at all — `verificationStatus` is fully guest-self-determined via a client-side checkbox with no cross-check against event configuration. Combined with the absent pre-loaded masterlist (AC2), "check in by name" performs no matching or validation of any kind; any guest can declare any name and any verification status for themselves.

**New finding: PA-213 (MEDIUM).** Once a check-in is created with `verificationStatus: 'flagged'`, there is no endpoint anywhere in the codebase — not in `guest-ops`, not in `live-ops`, not in `staffing-ops` — that can ever update it back to `'verified'`. A repo-wide search for any write to `verificationStatus` on a guest check-in outside of creation returns zero matches. Flagged walk-ins are permanently flagged; the AC's implicit premise (that PMCM/coordinator can review and clear a flagged walk-in) has no code path to act on, which compounds directly with PA-211 (no coordinator masterlist exists to even see the flag, let alone resolve it).

**New finding: PA-215 (MEDIUM).** `GuestWorkflowService.checkInByAccessCode` and `submitFeedbackByAccessCode` both call their `sideEffects` (`auditService.audit(...)`) directly inside `WorkflowCommandService.execute`'s `runWrite` (`workflow-command.service.ts:31-35`), with no `sideEffectMode: 'same_tx'` and no try/catch, *after* the `OpsGuestCheckIn`/`OpsGuestFeedback` row has already committed via Prisma. `AuditService.audit` itself does a read-then-write hash-chain append (`audit.service.ts`, reads the previous hash via `findFirst` then `create`s the new entry) with no locking — under concurrent check-ins this is a real race that can throw. If it does, the exception propagates unchanged through the controller to the guest-facing HTTP response (`apps/guest/src/app/dashboard/page.tsx:100-126`'s `checkIn()` catches it and calls `setError(...)`), falsely telling the guest their check-in failed when the row was already persisted. This is the same architectural shape already logged as **PA-187** in the EP-10 audit (client-side floor-plan-preference writes) — now confirmed as a second, independent call site of the same bug, in a different module (`guest-ops`), with a materially worse consequence: **`OpsGuestCheckIn` has no unique constraint on `(eventId, guestName)`**, so a guest who sees the false failure and re-submits creates a genuine duplicate row rather than being rejected, either inflating the attendance count or confusing registration desk staff about who has actually arrived.

## Cross-cutting checks

**1. Single source of truth for the attendance count — CONFIRMED, no drift risk found.** `OpsGuestCheckIn` (`apps/api/prisma/schema.prisma:915-934`) is the only Prisma model involved. `GuestWorkflowService.countCheckInsForEvent`/`listCheckInsForEvent` (`guest-workflow.service.ts:48-62`) is the only reader, and it is injected into and called identically by: the guest's own event view (`guest.controller.ts:12`), the coordinator role view and PMCM live-ops dashboard (`event-live-ops-read.service.ts:69,113,166,188`), and `event-read-models.service.ts`'s `defenseReadiness`/`pmcmEventWorkspace` (lines 117, 803-804, 829). All four consumers query the same table through the same service method — there are not three independently-maintained counts that could drift; there is exactly one. This is a genuinely clean piece of architecture and is called out explicitly so it isn't lost among this report's gaps — a first "no count-drift" contrast case worth keeping alongside the file's other positive contrast notes.

**2. resolveActor sweep cross-reference — mandatory, completed.** `guest-ops`'s three routes (`guest.controller.ts`) call `EventAccessPolicyService.resolveActor` **nowhere at all**, and this is **correct, not a gap** — guest check-in is unauthenticated by design (S02 AC1/AC6: no account, no role). This is the same "never wired to the shared auth system" shape already named in the EP-12 correction for `ai-governance`, but unlike `ai-governance` (which *should* have auth and doesn't), guest-ops's absence of `resolveActor` is the intended design for an anonymous, code-gated guest surface — do not conflate the two. The two backend paths that *do* read guest data on the coordinator/PMCM side (`getEventLiveOps` and `event-read-models`'s PMCM methods) were already swept and are already covered by PA-193 and PA-204 respectively; both now confirmed to include guest names/verification status specifically within their existing exposure, not as new PAs.

**3. Hardcoded-actor-identity check — no new instance found.** See S01's finding above: the absence of any coordinator-initiated guest write path means there is no fixed-identity attribution to find. Guest-initiated writes correctly audit as `actorRole: OpsUserRole.Guest` (`guest-workflow.service.ts:112,168`), which is accurate, not a misattributed hardcoded identity — the actor genuinely is an unauthenticated guest, and the guest's own name is captured separately as the audit's `affectedLabel`.

**4. "Different feature under the same name" check — does not apply.** S01's masterlist is a clean absence, not a relabeled or reused component (see S01 findings above).

**5. Guest-side data leakage — confirmed safe, with one clarification.** The guest-facing route never exposes other guests' data (S02 AC7 finding). The coordinator/PMCM-facing routes that do expose guest names (`getEventLiveOps`, `pmcmEventWorkspace`, `defenseReadiness`) are correctly scoped by role *in their explicit-check logic*, but inherit the pre-existing fail-open exposure of PA-193/PA-204 — an anonymous caller who reaches those endpoints via the known fail-open default receives guest names as part of the existing blast radius, not via any new leak introduced in this chain.

**New finding: PA-214 (LOW).** Headcount-only mode's absence (S02 AC3) is a confirmed, accurate gap already stated by the tracker itself — recorded here as its own PA per this initiative's convention of numbering confirmed absences on operationally significant AC items (same convention as PA-194/EP-11), not because it contradicts the tracker.

**New finding: PA-216 (HIGH) — new recurrence of the PA-186 masked-fallback shape, found in a different component than expected.** `apps/event/src/app/dashboard/EventDashboardClient.tsx:1553-1557` and `:1572` both call `loadEventCommandData(...).then(applyEventCommandData).catch(() => undefined)` — silently swallowing any rejection with no error state set and no logging. Confirmed directly by reading the file (not solely from the dispatched agent's report). The backend read models this feeds (`event-live-ops-read.service.ts:63-71`'s `Promise.all` inside `getEventLiveOps`, and `event-read-models.service.ts:115-120,801-805`'s `Promise.all` inside `defenseReadiness`/`pmcmEventWorkspace`) are all-or-nothing: if `guestReader.listCheckInsForEvent` fails for any reason, the entire read model throws — which then hits the silent `.catch(() => undefined)` on the frontend. The result: `live-operations-workspace.tsx:136` renders `liveOps?.guestAttendanceCount ?? 0`, showing a plausible-looking "0 guests checked in" (or a stale cached count, if one was already cached) with zero indication that the fetch failed. **This is not scoped to guest attendance alone** — because the backend `Promise.all` is all-or-nothing per read model, the same silent failure blanks out or stale-freezes the *entire* live-ops/defense-readiness panel (tasks, urgent issues, supplier statuses, coordinator assignments) whenever any one sub-query fails, not just the guest-count card. This is a second, independent recurrence of the exact shape already named PA-186 in the EP-10 audit — `coordinator-view.tsx` was checked specifically for this pattern and does **not** repeat it (it surfaces an explicit "Role-safe data unavailable" banner instead), but `EventDashboardClient.tsx` does, one layer up in the same feature area. The identical `.catch(() => undefined)` also recurs after mutating actions (`:1572`), meaning a failed post-action refresh is equally invisible to the PMCM Admin.
