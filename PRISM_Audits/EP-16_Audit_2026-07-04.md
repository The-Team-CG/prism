## Headline finding, before the per-story detail

This is the first epic in the entire initiative where all seven stories are
confirmed genuinely 0% real, independent of the tracker's own 0% claim. Every
prior epic audited (EP-01 through EP-15) found at least one story where the
tracker's percentage was wrong in one direction or the other. EP-16 is a
clean negative control across its full width, not because nothing was
checked closely, but because there is no story-specific code anywhere to
find: no new controller, no new service, no new endpoint, no new UI
component exists for any of the seven stories. The `ai-governance` module
that all seven depend on is real (confirmed in EP-12) but contains only the
PARE feature already audited last-but-two session; nothing has been added to
it for EP-16.

That said, "0% real" is not the same as "nothing to say." Five concrete,
non-absence findings came out of this audit: a mischaracterized feature
under a similar name (S05), two structural infrastructure gaps that block
multiple stories regardless of who builds them (no scheduler/trigger
mechanism, no model-selection mechanism), one UI-mounting-point gap for a
tracker-confirmed placement decision (S07's Drafts tray), and a newly
surfaced defect in PARE's own persistence layer that any future agent built
on the same pattern would inherit. These are recorded as PA-242 through
PA-246 below.

## New findings (PA-242 through PA-246)

**PA-242 (MEDIUM, EP-16-S05).** The only "reliability score" calculation in the codebase (`supplier-finder.agent.ts:83-91`) is a different, simpler feature than the one this story specifies: a naive rating average with no Bayesian confidence band, no minimum-count gate, and no supplier-profile visibility, used solely for internal PARE candidate ranking. Any future build of this story must not mistake the existing field name for a head start on the actual requirement.

**PA-243 (HIGH, blocks EP-16-S01 and EP-16-S07 structurally).** No scheduler (`@nestjs/schedule`, cron, or equivalent) and no event-emitter/hook mechanism exists anywhere in `apps/api`. This is not "the trigger logic for these two stories hasn't been written yet" — it is that the entire mechanism class (background/scheduled execution, or fire-on-create hooks) that both stories' automatic-trigger ACs assume is available does not exist in this codebase at all. Whoever builds either story first will need to introduce this infrastructure from scratch, and it should be built once, shared, not per-story.

**PA-244 (MEDIUM, blocks model differentiation across EP-16).** No model-selection code exists; every live Claude call in the repo hardcodes `'claude-sonnet-4-6'` (all five PARE agents). Three of EP-16's seven stories specify the Haiku model by name for cost/latency reasons; building any of them today would require introducing per-feature model configuration for the first time, not just supplying a different string in an existing parameter.

**PA-245 (LOW-MEDIUM, EP-16-S07).** `EventCommandInbox` has no tab, tray, or non-severity grouping structure. The tracker's own coordination note treats the Drafts-tray placement decision as settled ("Francis confirms dashboard UI placement... coordination must occur at C4 start"), but the component that placement refers to would need new structure added, not an existing slot filled.

**PA-246 (HIGH, pre-existing PARE code, relevant to EP-16 as inherited risk).** Dispatched `ecc:silent-failure-hunter` against the `ai-governance` module per this session's standing check. It found a new, backend-side variant of the tracked Shape A pattern (a silent catch masking failure as an indistinguishable success state), not previously seen outside `apps/event` frontend code: `PAREService`'s private `dbCreate`/`dbUpdate` helpers (`pare.service.ts:63-82`, reused by `getPendingApprovals`/`findAuditLog` at lines 172-176 and 211-222) wrap every Prisma call in a bare `catch {}` with no logging, silently rerouting the write to an in-memory `Map` on any DB failure. The caller receives an object indistinguishable from a real persisted row; a DB outage would silently and permanently drop AI approval/audit records (lost on process restart) with zero operator visibility, on exactly the data meant to be this system's compliance trail for AI actions. Related, not-yet-atomic writes were also found: `approveRecommendation`/`rejectRecommendation` (lines 180-204) update the approval record and its linked audit log as two separate, non-transactional calls, so a DB/memory split between them is possible and invisible; `AiGovernanceService.runDryRun` (`ai-governance.service.ts:67-96`) similarly creates an audit log then an approval record as two sequential, non-transactional writes, so a failure on the second orphans the first in `pending_human_approval` forever; `EventContextAgent` and `SupplierFinderAgent` both swallow DB errors into an empty/zero result indistinguishable from a legitimate "no data" outcome, which then drives budget-feasibility and risk-escalation logic shown to the human approver. **Per this session's standing instruction, this is logged as an addition to the existing pending Shape A/B sweep, not a new escalation trigger** (that sweep was already triggered at EP-14 and remains not-yet-performed). Shape A's confirmed-instance count moves from 3 to 4 with this entry, and for the first time includes a backend instance, not just frontend. Directly relevant to EP-16 because any of the seven stories built by extending PARE's existing agent pattern would inherit this same silent-degrade behavior on day one.

## Summary

EP-16 is this initiative's first full-width negative control: all seven
stories are genuinely at 0%, and the tracker's own claim is accurate for
every one of them, a notable contrast to every epic audited before it, where
at least one story's real completion diverged sharply from its tracked
percentage. That accuracy should not be read as "nothing worth fixing here."
Five concrete findings came out of this audit that matter more than the
absence itself: EP-16-S05 is quietly mislabeled against an existing
same-named field (PA-242); two structural mechanisms this epic assumes
exist, a scheduler/trigger system and a model-selection system, do not exist
anywhere in the codebase and will need to be built once, shared, rather than
reinvented per story (PA-243, PA-244); the tracker's own "confirmed" UI
placement for S07's Drafts tray requires new structure, not an existing slot
(PA-245); and the standing silent-failure check, extended into PARE's
existing persistence layer for the first time this session, surfaced a
backend-side instance of the Shape A pattern that directly threatens the
compliance trail for every AI action this system will ever take, human
approval gate included, since a record that silently and permanently
vanishes into memory on a DB hiccup is not meaningfully different from one
that was never approved at all (PA-246). Every one of EP-16's seven stories
inherits EP-15-S05's already-confirmed-broken DataSanitizer/ZDR gate and
PA-207's compromised approval-identity check the moment any of them is
actually built; none of that has changed this session, and this audit adds
one more reason, PA-246, why the foundation itself needs attention before
any of the seven stories should be started in earnest.
