# EP-17 Audit — Platform and Backend Architecture — 2026-07-04

**Last confirmed PA before this audit:** PA-246 (`_Audit_Index.md`, EP-16 row, verified
directly). New PAs in this report: **PA-247 through PA-250.**

Scope: EP-17-S01 through EP-17-S03, closing EP-17 as a full epic (3 stories, no chain split).

## Headline finding, before the per-story detail

This epic inverts the pattern seen in every prior epic this initiative. EP-16 was the first
full-width negative control (tracker's 0% claims all confirmed accurate). EP-17 is the
opposite: two of its three stories (S02, S03) are tracked **Blocked, 0%**, and direct
inspection of the actual codebase, backed by a passing build, a passing 605-file boundary
check, and a passing 230-test suite, shows both are **essentially fully implemented and
working**. This is the largest tracker-accuracy gap found this entire initiative, and it runs
in the direction of under-claiming, not over-claiming. The root cause is traceable: the
planning documents referenced by the tracker's own commentary have checkboxes that were never
updated after the real work landed. See the new "Plan-Checkbox Staleness" pattern below
(PA-249).

## EP-17-S02 — Event-Ops Retirement and Sample-Compatibility Module

**Tracker claim:** Blocked, 0%, Owner Anthony, dependency EP-17-S01.

**Verified directly against the actual codebase, not against File 55's own checkbox state:**

1. `SampleCompatibilityModule` (`apps/api/libs/modules/sample-compatibility/src/sample-compatibility.module.ts`)
   exists and imports exactly the 19 capability modules named in the plan: `EventCoreModule`,
   `TrustOpsModule`, `NotificationOpsModule`, `AccessControlModule`, `IdentityOpsModule`,
   `InquiryOnboardingModule`, `CommercialOpsModule`, `ComplianceOpsModule`, `FloorplanModule`,
   `FileOpsModule`, `FinanceOpsModule`, `GuestOpsModule`, `StaffingOpsModule`,
   `SupplierOpsModule`, `AiGovernanceModule`, `LiveOpsModule`, `ClosureOpsModule`,
   `EventReadModelsModule`, plus `DatabaseModule`. No circular-dependency failure: the build
   passes and `check:boundaries` passes clean.
2. `SampleController`, `SampleCompatibilityService`, `SampleStateService` all live under
   `sample-compatibility/src/`, confirmed by direct file read, not by trusting the plan's
   "Implementation Status" summary alone.
3. `apps/api/apps/api/src/app.module.ts` imports `SampleCompatibilityModule`, confirmed by
   direct grep of the file (line 10 import, line 54 module registration). `EventOpsModule` does
   not appear anywhere in `apps/api`, `packages`, or `scripts` (confirmed by a zero-match
   repo-wide grep for `EventOpsModule|EventOpsService|@prism/modules/event-ops|EVENT_OPS_CONTROLLERS`).
4. `event-ops` folder: **does not exist.** Not "reduced to index-only" as the AC allows for,
   fully absent.
5. `event-ops-client.ts` rename decision (PA-131): the target-shape plan documents the decision
   explicitly — kept as the public API-client compatibility name because exported package
   consumers still import it, with route paths unchanged. Documented and implemented as stated.
6. `test:event-ops` suite: does not exist (see S01). Its successor, `test:sample-compatibility`,
   passes 66/66.
7. File 55's task checkboxes: **every single task-level checkbox across all 11 tasks in
   `2026-06-22-prism-event-ops-target-shape-plan.md` remains `[ ]` unchecked**, despite the
   document's own top-of-file "Implementation Status" section stating the work is done. Real
   code proves the "Implementation Status" summary is the accurate account, and the granular
   task checkboxes below it were simply never updated after the work landed. This is the
   opposite of what the tracker's own note assumed ("Master plan checkbox NOT authoritative")
   — see PA-249.

**Sample-endpoint connection, confirmed directly (the additional lead for this story):**
`SampleController` (`sample-compatibility/src/controllers/sample.controller.ts`) owns exactly
`GET /sample/state`, `POST /sample/reset`, `POST /sample/seed`, calling
`SampleCompatibilityService.state()`/`resetSample()`/`seedSampleState()` with **no actor
parameter, no role check, and no call to `resolveActor` anywhere in that call path** (confirmed
by direct read of `sample-compatibility.service.ts` lines 632-690). This **is** the location of
the two unauthenticated `/sample/reset` and `/sample/seed` endpoints already sitting on
Francis's pending resolveActor escalation. This is not a new, separate defect discovered here —
it is confirmation that this story's own "Done" deliverable and that pending escalation item
are the same underlying exposure, recorded as **PA-250**. Everything else in
`SampleCompatibilityService` (the ~30 other private methods reusing `resolveActor` for audit
logs, privacy requests, onboarding, etc.) is dead code never reachable from `SampleController`,
consistent with the 2026-07-04 ResolveActor Sweep's existing finding that this file's other
call sites are unused.

**Real completion: ~95-100%, not 0%.** Recorded as **PA-247**. Every AC item checked against
real code holds; the only imperfection is that the child plan's own execution record was never
updated to reflect it. **Recommended status: In Review, not Done.** Functional completeness
verified by this audit does not substitute for the second-owner review the Cadence Review
Guide's Standing Rules 2 and 7 require before a Done call; this audit is not that review.

## EP-17-S03 — Guest-Ops Module Implementation and Verification

**Tracker claim:** Blocked, 0%, Owner Anthony, dependency EP-17-S01.

**Verified directly:**

1. `GuestWorkflowService` (`apps/api/libs/modules/guest-ops/src/services/guest-workflow.service.ts`)
   is real, complete code, not a planning-doc reference. Has its own test file
   (`guest-workflow.service.test.ts`).
2. `GUEST_COMMANDS` and `GUEST_READER` tokens: bound in `guest-ops.module.ts` via
   `{ provide: GUEST_COMMANDS, useExisting: GuestWorkflowService }` and the equivalent for
   `GUEST_READER`, both exported. The build passes clean, confirming no unbound-token failure
   on module load.
3. `EventReadModelsService` injects `GUEST_READER` (confirmed present in
   `event-read-models.service.ts` by direct grep), consistent with the plan's Phase 11
   cross-reference (PA-123) — no conflict found.
4. Guest actor cannot reach PMCM planning/live payload: confirmed structurally, not via a role
   check (correct, per the standing EP-13 finding that guest-ops legitimately has no
   `resolveActor` call by design). `OpsGuestController` exposes exactly three routes — event
   lookup by access code, check-in, feedback — each returning only a narrow guest-mapped shape
   (`mapGuestEvent`/`mapGuestCheckIn`/`mapGuestFeedback`). There is no route on this controller
   that could return a PMCM/live-ops payload; the boundary is enforced by what the controller
   does not expose, not by an access check on what it does.
5. Privacy consent gate: real and enforced. `checkInByAccessCode` and
   `submitFeedbackByAccessCode` both throw `BadRequestException` with an explicit message
   ("Privacy consent is required before guest check-in"/"...feedback submission") when
   `privacyConsentAccepted` is falsy, confirmed by direct code read
   (`guest-workflow.service.ts:87-89, 136-138`).
6. `mapGuestEvent` (`guest-workflow.service.ts:209-226`) returns exactly: `id`, `eventName`,
   `eventDate`, `clientName`, `readiness`, `floorPlanStatus`, `activeFloorPlanDraftId`,
   `guestAccessCode`, `attendanceCount`. No `privateNotes`, budget, staffing, or supplier field
   present — confirmed by direct inspection of the actual object literal, not by trusting the
   AC's description of what it should exclude.
7. `GuestOpsModule` imports `FileOpsModule` (`guest-ops.module.ts:11`), with a real rationale
   confirmed by code: `GuestWorkflowService.submitFeedbackByAccessCode` calls
   `DocumentVaultService.validateUploadMetadata` for guest feedback photo/video uploads. PA-121
   resolved by direct inspection.
8. `test:event-ops` count: reused from S01 rather than re-run, per this audit's own discipline
   instruction — 230 tests, 65 files, all passing, is the current real baseline and includes
   guest-ops's own test files.

**Real completion: ~100%, not 0%.** Recorded as **PA-248**. Every AC item checked against real
code holds. **Recommended status: In Review, not Done**, for the same reason as S02: the
Cadence Review Guide's Standing Rules 2 and 7 require a second-owner review before a Done call,
and this audit does not constitute that review.

## New findings (PA-247 through PA-250)

**PA-247 (HIGH, tracker-reliability, EP-17-S02).** Tracker claims Blocked/0%; real code shows
`SampleCompatibilityModule` fully built, wired into `AppModule`, importing all 19 named
capability modules with no circular dependency, `event-ops` fully deleted (not merely reduced),
and its own successor test suite (66 tests) passing. Real completion ~95-100%.

**PA-248 (HIGH, tracker-reliability, EP-17-S03).** Tracker claims Blocked/0%; real code shows
`guest-ops` fully implemented: `GuestWorkflowService` real and tested, `GUEST_COMMANDS`/
`GUEST_READER` properly bound, `EventReadModelsService` consuming the reader port, privacy
consent gate enforced, guest-facing payload correctly excludes PMCM-private fields, and
`FileOpsModule` import justified by real upload-validation code. Real completion ~100%.

**PA-249 (MEDIUM, new tracked pattern: "Plan-Checkbox Staleness").** This epic's own tracker
notes assumed a "master plan overclaims, child plan is the authoritative source" shape for both
S02 and S03. Direct inspection of real code shows the opposite: for both stories, the granular
task-level checkboxes inside the child plan documents (`phase-9-guest-ops.md`,
`prism-event-ops-target-shape-plan.md`) remain entirely unchecked, while the actual
implementation is complete and working. The master plan's own top-level summary language (for
S02, its "Implementation Status" block; for S01, its Phase 13 progress note) turned out to be
the more accurate account in both cases audited here. **Naming this as its own pattern for
future audits, per this session's instruction:** plan-tracking checkboxes in this repo, whether
in the master plan or a child plan, do not reliably indicate real completion state in either
direction. Only the code, the build, the boundary check, and the test suite are authoritative.
A future audit should not assume either document's checkbox state without checking real code,
exactly as this initiative has already learned to do with the AC tracker itself.

**Rule-level callout, not a two-story footnote:** this finding **reverses the Cadence Review
Guide's own Standing Rule 1** ("child plan checkboxes are authoritative, master plan claims are
not sufficient"). It is not that `phase-9-guest-ops.md` and
`prism-event-ops-target-shape-plan.md` merely happened to be stale this one time — the rule
itself, as written, points the wrong way for both stories this audit checked it against.
Whoever reads the escalation bundle this finding feeds into should treat PA-249 as a correction
to a standing rule, not as an observation scoped to these two plans. Until Standing Rule 1 is
itself revised, any story whose Done/Blocked call rests on "the child plan's checkboxes say so"
should be re-verified against real code before that call is trusted.

**PA-250 (CRITICAL, confirms and locates a previously-general finding).** The two
unauthenticated `/sample/reset` and `/sample/seed` endpoints already carried on Francis's
pending resolveActor escalation are confirmed to live inside `SampleCompatibilityModule`'s
`SampleController`, calling `SampleCompatibilityService.state()`/`resetSample()`/
`seedSampleState()` with zero actor resolution anywhere in the call path. This module is
EP-17-S02's own primary deliverable. The escalation item and this story's real completion
status are the same underlying object, not two separate concerns — correcting EP-17-S02's
tracked status to reflect its real ~95-100% completion should not be read as resolving this
exposure; the exposure ships as part of that same real, working code today.

## Summary

EP-17 closes with this initiative's largest tracker-accuracy gap yet, and for the first time
the gap runs toward under-claiming rather than over-claiming: two stories tracked Blocked/0%
(S02, S03) are both essentially complete, verified not by trusting either plan document but by
running the actual build, the actual 605-file boundary check, and the actual 230-test suite
directly. EP-17-S01's Done/100% claim holds up under the same regression scrutiny every other
Done story this initiative has received, and should stand. The mechanism behind S02 and S03's
miscount is now named as its own pattern, Plan-Checkbox Staleness (PA-249): neither the master
plan's summary language nor a child plan's granular checkboxes reliably track real completion
in this repo, and only the code itself is authoritative, a lesson this initiative already
learned once about the AC tracker and must now extend to the planning documents underneath it.
The one finding that matters most going forward is PA-250: the pending resolveActor escalation's
two unauthenticated sample endpoints are not a separate, still-abstract risk sitting alongside
EP-17-S02, they are that story's own real, working, currently-shipping deliverable. Correcting
this story's tracked status to reflect how complete it actually is does not make that exposure
any less live.
