## STORY 2: EP-14-S02 — Post-event document completion and filing

**Files checked:** `apps/api/libs/modules/closure-ops/src/services/event-closure.service.ts`'s `completePostEventDocument` (lines 80-100), `apps/api/libs/modules/closure-ops/src/controllers/event-closure.controller.ts`'s matching route (lines 18-25), `apps/api/prisma/schema.prisma`'s `OpsPostEventDocument` model (lines 826-837), `apps/event/src/app/dashboard/EventDashboardClient.tsx` (the `postEventDocuments` File Hub mapping, lines 644-657), a repo-wide search of `apps/client` for any acknowledgment-related component.

| AC | Verdict | Evidence |
|---|---|---|
| 1. Tracker accessible from apps/event after S01's archive gate | **FAIL** | No dedicated post-event-document tracker component exists anywhere in `apps/event`. `postEventDocuments` are rendered as passive rows inside a generic "File Hub" list (`EventDashboardClient.tsx:644-656`) alongside invoices, floorplans, and contracts — not a distinct tracker, and not gated on the archive event having occurred (the File Hub renders these documents regardless of `event.archived`). |
| 2. Tracker shows Pending/Submitted/Overdue | **PARTIAL — two of three states are structurally possible, the third is not** | `OpsPostEventDocument.status` (`schema.prisma:830`) defaults to `'pending'`; `completePostEventDocument` sets it to `'submitted'`. **No code anywhere ever sets or computes an `'overdue'` value** — there is no due-date field on the model at all (see PA-226), so "Overdue" cannot be derived even in principle without a schema change. |
| 3. PMCM Admin can submit/upload against tracker entry, records timestamp + admin identity | **FAIL on both halves of the record-keeping requirement** | `completePostEventDocument` is real and does flip status to `'submitted'`, but the Prisma model has **no `submittedAt` or `submittedBy` column at all** — even if the service wanted to record either, there is nowhere to write it on the record itself. The only trace of the action is an audit-log entry (see PA-223), not a field on the document. |
| 4. 3-5 day endorsement window, Deadline Overdue alert if missed | **FAIL, confirmed absent** | No due-date field, no window-length constant, no alert/notification logic referencing this document type anywhere in `closure-ops` or `notification-ops`. |
| 5. Client can acknowledge receipt from client portal, recorded with timestamp | **FAIL, confirmed absent** | No acknowledgment endpoint exists anywhere in `apps/api`. A repo-wide search of `apps/client/src` for any post-event-document or acknowledgment component returns only type/mock references (`prism-sample-state.ts`, `prism-api.ts` type defs) — no actual UI component. The Prisma model has no `acknowledgedAt`/`acknowledgedBy` field to record one even if a UI existed. |
| 6. PMCM Admin notified when client acknowledges | **N/A** | Nothing to notify about — AC5 doesn't exist. |
| 7. Filed documents retrievable per event by PMCM Admin, denied to supplier/coordinator/guest | **PARTIAL** | PMCM Admin can retrieve them today via the File Hub mapping (read access holds). No explicit code path exposes `postEventDocuments` to supplier, coordinator, or guest actors in any of the read models checked this or prior sessions — access denial holds by omission, not by an explicit gate, since nothing offers this data to those roles in the first place. |

**"Code built ahead of its stated gate" check, as specifically requested:** confirmed — `completePostEventDocument` is real, callable code that exists independent of S01's archive gate ever having run (it has no dependency check on `event.archived` at all), consistent with the pattern already seen elsewhere this initiative (code existing ahead of its tracker-stated dependency). However, unlike those prior cases, this doesn't represent meaningfully more of the *story* being done — the endpoint is a single, unauthenticated status flip against a schema with none of the fields the rest of the story's ACs require.

**New finding: PA-222 (CRITICAL).** `completePostEventDocument` (`PATCH /:eventId/post-event-documents/:documentId/complete`) has **zero actor resolution or role check of any kind** — confirmed directly: the controller method takes no actor parameter, and the service method never calls `resolveActor` or any guard. Any anonymous caller can mark any post-event document, for any event, as submitted. `GET /:eventId/close-gates` shares the identical shape — the controller method also takes no actor parameter, and `closeGates`/`FileRequirementsMatrixService.closeGates` never resolve or check an actor either, exposing per-event document/billing/floorplan/supplier-review closure readiness to anonymous callers. This is a **third confirmed instance of the "skips the shared resolver entirely" shape** (after PA-135/136's coordinator-assignment endpoints and PA-162's `/ai/pare/*`), and a fourth call site within it (`closeGates` alongside `completePostEventDocument`).

**New finding: PA-223 (MEDIUM).** `completePostEventDocument`'s audit-log side effect (`event-closure.service.ts:97`) hardcodes the actor name as the **literal string `'PMCM Admin'`**, regardless of who actually invoked the (unauthenticated — PA-222) endpoint. Confirmed instance of the hardcoded-actor-identity pattern already documented multiple times this initiative, now found in `closure-ops` specifically.

**New finding: PA-226 (HIGH).** `OpsPostEventDocument`'s Prisma schema (`schema.prisma:826-837`) has only `id`, `eventId`, `title`, and `status` — no due-date, no `submittedAt`/`submittedBy`, no `acknowledgedAt`/`acknowledgedBy` field of any kind. This makes AC2 (Overdue status), AC3 (timestamp + submitting-admin identity on the record), AC4 (endorsement window + deadline alert), and AC5 (client acknowledgment) all **structurally impossible today without a schema migration** — this is not a service-layer or UI-layer gap that could be closed by writing more application code against the existing model; the data has nowhere to live yet.

## Cross-cutting checks

**1. Standing check — both tracked shapes independently reach a THIRD confirmed instance in this epic. Escalation triggered, as the standing check's own rule requires.**

- **Shape A (silent-swallow catch masking failure as an indistinguishable pending/empty state): THIRD instance confirmed.** `apps/event/src/app/components/pmcm/phase4-workspace.tsx:93-94` — `void onLoadCloseGates().then(setCloseGates).catch(() => setCloseGates(null))` and `void onLoadInsights().then(setLocalInsights).catch(() => setLocalInsights(insights))`. `closeGates` initializes to `null` (`:87`) and the failure-path reset is also `null` — the rendered "Close gates" card (`:110`) shows `closeGates ? "X/Y" : "Loading"`, meaning a permanently failed fetch is indistinguishable from a fetch still in flight, with no error ever surfaced to the PMCM Admin. Verified independently via a dispatched `ecc:silent-failure-hunter` agent, which confirmed this reading against the full file. (Prior instances: EP-10-S01's original case; `EventDashboardClient.tsx:1553-1557,1572`/PA-216.)
- **Shape B (unguarded post-commit side effect): THIRD instance confirmed.** `apps/api/libs/modules/closure-ops/src/services/event-closure.service.ts` — `archiveEvent`, `generateEventInsights`, and `completePostEventDocument` **all three** run their `sideEffects` callback (audit-log call, and for `archiveEvent` also a notification-queue call via `Promise.all`) inside `WorkflowCommandService.execute`'s `runWrite` with no `sideEffectMode: 'same_tx'` and no try/catch, after their respective Prisma writes have already committed. Traced mechanically through `workflow-command.service.ts:31-40` and independently confirmed via the dispatched agent: if the audit or notification call throws, the exception propagates out of `execute()` as an operation failure even though the event was already archived / the insight already generated / the document already marked submitted. (Prior instances: an EP-10 client-ops case; `guest-workflow.service.ts`'s two call sites/PA-215.)

**Per the standing check's own escalation rule, this now warrants a dedicated codebase-wide sweep for both shapes** — the same treatment the resolveActor pattern received after its third incidental discovery. **New finding: PA-224 (Shape A, MEDIUM, escalation flag)** and **PA-225 (Shape B, MEDIUM, escalation flag)** are recorded to mark these as the third instances specifically, distinct from simply adding two more individual bugs to the pile — the recommendation, consistent with how the resolveActor sweep was framed, is to fix each shape once at a shared layer (a wrapped fetch helper for Shape A; a `WorkflowCommandService` option that catches/logs side-effect failures without failing the caller for Shape B) rather than patching each of the now six known call sites individually.

**2. resolveActor cross-reference.** `archiveEvent`, `listEventInsights`, and `generateEventInsights` are the closure-ops sites already covered by **PA-202** from the 2026-07-04 sweep (row 50-52 in that report) — confirmed unchanged, with PA-221 above refining `archiveEvent`'s specific sub-shape. `completePostEventDocument` and `closeGates` are **not** in the sweep's 60-site table at all, because they never call `resolveActor` in the first place — this is the "skips the resolver entirely" shape (PA-222), a different category the sweep's own methodology correctly wouldn't have caught (the sweep searched for `resolveActor` call sites; these two have none to find).

**3. Hardcoded-actor-identity check.** Confirmed present — see PA-223. `archiveEvent`'s own audit call, by contrast, does capture a real (if unauthenticated) `actorName` value rather than a hardcoded string, so this specific defect is scoped to `completePostEventDocument` only, not the whole module.

**4. "Right feature, wrong actor or architecture" check (Event Insights Card vs. EP-16-S06's AI upgrade).** `OpsEventInsight`'s schema and `generateEventInsights`'s `upsert` (one row per `eventId`, `where: { eventId }`) is a genuinely reasonable foundation for a later AI-upgraded version to extend — the same row could plausibly gain an `aiSummary`/`aiGeneratedAt` sibling field without restructuring. This is architecturally sound as a base layer, though EP-16-S06 itself doesn't exist yet (confirmed by the same repo-wide AI-reference search under AC7) so this can't be verified as *actually* wired that way, only as *plausible* given the current shape.

**5. AI-boundary check.** Confirmed to hold — see AC7 above. Zero AI/Claude API calls exist anywhere in `closure-ops`.
