## Executive summary

**PARE (EP-12-S02) is the first AI-feature story audited this initiative, and it fails on exactly the two governance mechanisms that exist specifically to make an AI feature safe to run: DataSanitizer and ZDR confirmation are both non-functional, not merely unverified.** The 5-agent orchestrator itself is real, well-built code — `BudgetAgent`, `RiskAgent`, and `MessageDrafterAgent` each run genuine Claude tool-use loops in live mode. But `DataSanitizerService.sanitize()` is called exactly once in the entire flow, after all five agents have already completed, purely to redact the copy stored in `OpsAiAuditLog` — it is never applied to the context sent to the actual Claude API calls. Client names, client preferences, and full event/supplier detail go out over the wire unsanitized in live mode. Separately, `zdrConfirmed` is a hardcoded boolean with inverted logic: `true` in mock mode (which never calls a real API) and `false` in live mode (which does) — there is no code anywhere that verifies ZDR status before a run proceeds; the field is written after the fact, not checked before. And the `/ai/pare/*` controller — already flagged zero-auth in EP-07 Chain A (PA-162) — is confirmed unchanged today, with the added detail that its approve/reject endpoints accept the approver's identity as a bare, unauthenticated query-string parameter defaulting to `'PMCM Admin'`.

**The freeze-window/Emergency Change concept that EP-12-S02 and EP-12-S03 both depend on does not exist anywhere in the codebase.** A repo-wide search for "freeze" or "Emergency Change" in any form returns zero matches. PARE is not gated by a freeze window because there is no freeze window to gate on — `SupplierNetworkWorkflowService.withdrawSupplier` triggers `PAREService.handleEmergencyTrigger` unconditionally on every withdrawal, regardless of timing. This is not "two features that only look connected" in the usual sense of this audit initiative's click-path checks — it's one feature (PARE triggering) with no dependency on a second feature that was never built at all.

**EP-12-S03 (tracked Done/100%) has two regression-worthy gaps a "Done" label should not carry.** Withdrawal has no mandatory-reason validation — a caller can omit `reason` entirely and the system silently substitutes a filler string rather than rejecting the request. And there is no supplier self-service withdrawal path anywhere in the codebase (confirmed by a search of `apps/supplier`) — the only withdrawal endpoint is PMCM-Admin/System-initiated, which contradicts AC-5's premise that a supplier withdraws from their own assigned events. This is the "right feature, wrong actor" pattern first named in the EP-11 audit, now found in a story marked fully Done.

**EP-12-S04, S05, and S06 are confirmed at or near zero, consistent with the tracker.** EP-11-S05 already established that no distinct EDSO role view exists on the coordinator side; this audit confirms the PMCM side has no EDSO-specific surface either — "Event Day System Operator" appears only as one selectable string in a generic role dropdown. No 2-minute auto-approval concept exists anywhere. EP-12-S05's five named game templates and EP-12-S06's AI monitoring agent both return zero matches on an exhaustive search — two more genuine negative controls for this initiative, alongside EP-07 Chain B and EP-10-S03.

## Cross-cutting: ai-governance auth pattern (new ground, per the brief)

Checked explicitly since `ai-governance` was not one of the 12 modules named in the ResolveActor Sweep. **`ai-governance` does not call `EventAccessPolicyService.resolveActor` at all, anywhere.** `OpsAiGovernanceController`'s one route (`POST /ai/governance/dry-run`) takes a body DTO and calls `aiGovernanceService.runDryRun(dto)` with no actor resolution, no role check, nothing — a third distinct failure mode alongside "fail-open default satisfied" (the sweep's 52 sites) and "skips the shared resolver entirely" (PA-135/136, PA-162): **`ai-governance` has literally never been wired to any auth mechanism at all, not even one that could later be discovered fail-open.** `PAREService` itself (the class, as opposed to the controller in front of it) has no auth of its own either — it trusts whatever actor context its caller supplies, which in the one real call path (`supplier-network-workflow.service.ts` → `handleEmergencyTrigger`) is not actor-scoped at all; the method takes no actor parameter. The actual exposure for PARE lives entirely in the `/ai/pare/*` controller (PA-162, reconfirmed above), not in `ai-governance` itself — `ai-governance.controller.ts`'s own `dry-run` endpoint is a separate, equally unauthenticated surface, but its blast radius is limited to a dry-run (no real mutation traced this pass; not independently numbered given the story scope, but worth noting for a future audit of whatever story owns `ai-governance.service.ts`'s `runDryRun`).
