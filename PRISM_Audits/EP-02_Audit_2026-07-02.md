## EP-02-S02 — Error State Handling

**Tracker Claim:** Done, 100%. Distinct visible error state on fetch failure, no raw error/stack exposed, recovers without full reload. Commit e0f99c0.

**Repo Reality (via `ecc:silent-failure-hunter` findings, independently verified by direct read):**
- `event-command-inbox.tsx:105-112`: on `loadFailed`, shows a generic "Could not load inbox / Try refreshing." — confirmed no raw error message or stack trace is ever passed to the UI. This part of the claim holds.
- **AC item 1 ("distinct error state") does not actually hold as claimed.** `EventDashboardClient.tsx:1390-1409`: `Promise.all([loadPmcmState, loadApprovalRequests, loadCommandInbox])` feeds one shared `.catch` that unconditionally sets `commandInboxLoadFailed = true`, regardless of which of the three unrelated fetches actually failed. Verified directly: if PMCM state or approvals fail while the inbox call itself succeeds, the inbox will still incorrectly show an error state. Conversely, if only the inbox fetch fails, `Promise.all` rejects before the other two results are read — those two data sources get no distinct error indicator of their own, they just silently keep whatever stale/cached values they had. This is not a "distinct" per-source error state; it's one shared flag with a misleading name.
- **Verified silent failure, not on tracker:** `EventDashboardClient.tsx:2067`, the manual refresh handler: `.catch(() => setCommandInboxLoadFailed(true))` — the actual error object is discarded entirely, no `console.error`, no logging call. Ops has zero diagnostic trail when refresh repeatedly fails.
- **Dead code, false confidence risk:** `apps/event/src/features/event-dashboard/use-pmcm-command-inbox.ts` implements a clean, correct per-source `onError` hook pattern — but it is never imported or used anywhere in the app. If this Done claim was verified against this hook rather than the actual wired code path in `EventDashboardClient.tsx`, that would explain the mismatch between the claim and reality.

**Mismatch:** Tracker overclaims "distinct" error state — it is a single conflated flag across three unrelated data sources, and one failure path silently discards its error entirely.

**Regression Check:** No dedicated test exists for any of this (see Regression section below) — cannot regression-test something with zero coverage. Commit e0f99c0's amber-alert/badge UI itself renders correctly when `loadFailed` is true; the defect is in *what sets* `loadFailed`, not the rendering.

## EP-02-S03 — Click-Through Navigation

**Tracker Claim:** Done, 100%. Each item clickable, navigates to correct workspace section, preserves inbox state on return, stale-item click handled gracefully, non-PMCM actors blocked from triggering routes. Commit a97498f.

**Repo Reality:**
- `event-command-inbox.tsx:64`: `return item.href ? <Link href={item.href} className="block">{card}</Link> : card;` — confirmed, items conditionally wrap in `Link` using `item.href` exactly as claimed.
- "Preserves inbox state on return": confirmed architecturally sound. Because `EventDashboardClient` is mounted at the `layout.tsx` level (persists across all `/dashboard/*` client-side navigations) rather than per-page, it does not unmount/remount on navigation away and back — its in-memory `commandInbox` state and cache (`commandInboxCache`) survive round-trips without a fresh refetch, satisfying this AC by construction.
- "Non-PMCM actors cannot trigger navigation routes": the inbox's own read endpoint is gated server-side (see S01). Destination routes (e.g., `/dashboard/inquiries`) were not individually re-audited for role gating in this pass — the broader event-read-models test suite (41/41 passing) shows this role-check pattern applied consistently elsewhere in the same module family, but this was not exhaustively re-verified per destination route.
- "Stale/resolved item click either routes correctly or shows a clear message": not independently verified this pass — no code path was found that specifically detects "this item's underlying record is now stale" before navigating; the `href` is a static string generated at inbox-build time, so a stale item would simply navigate to the (now possibly-changed) underlying record's normal page rather than erroring. Whether that "counts" as an AC pass depends on interpretation the tracker doesn't make testable.

**Mismatch:** No overclaiming found for the specific behavior that was checked (Link-wrapping is real). The "stale item" and "non-PMCM destination route" sub-claims are plausible but not independently proven false or true — flagged as unverified rather than confirmed.

**Regression Check:** No dedicated test exists for click-through behavior at all (see Regression section).

## Most Severe Items for Follow-Up

1. **`event-coordinator-assignments.controller.ts` has zero authorization on both its POST (assign) and PATCH (acknowledge) endpoints** — any caller can assign or acknowledge coordinator staffing for any event. This is the same class of defect as EP-01's `uploadConforme` gap; it's now been found in two separate epics, suggesting a systemic pattern worth a repo-wide sweep for "endpoint exists, no `requireActorRole` call."
2. **S04 was marked Done by bypassing its own explicitly-stated second-owner-confirmation requirement**, in direct violation of documented team policy (`AC_Tracker_Cadence_Review_Guide.md:66`). This is a process failure that could be hiding in other "self-resolved as non-issue" stories — worth auditing whether this pattern recurs elsewhere.
3. **EP-01-S02's withdrawal/replacement equivalent — here, EP-02-S05's FR-89 — is completely unimplemented** despite schema columns existing for it, which tends to produce false confidence that the feature is "mostly there."
4. **S02's error-state AC is not actually met as specified** — a single conflated error flag across three unrelated data sources will show false error states and miss real ones depending on which of three concurrent fetches fails.
5. Frontend test coverage remains at **zero** across both `apps/client` and `apps/event` — every UI-layer defect found in this and the EP-01 audit exists with no regression protection at all.
