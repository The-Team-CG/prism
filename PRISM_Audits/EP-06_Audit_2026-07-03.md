## Standing check — auth-gap sweep (6th confirmed area, and the root cause is now centralized)

`compliance-rules.controller.ts` (`listComplianceRules`, `createComplianceRule`, `updateComplianceRule`) is correctly gated — each calls `requireActorRole([PmcmAdmin, System])` and it's awaited (`compliance-workflow.service.ts:44-48, 59-65, 102-107`).

**But** `event-compliance.controller.ts`'s two endpoints — `runCompliance` (`POST /events/:eventId/compliance`) and `resolveCompliance` (`PATCH /events/:eventId/compliance/:checkId`) — resolve no actor and enforce no role at all. In `compliance-workflow.service.ts`, neither `runCompliance` (128-188) nor `resolveCompliance` (190-246) supplies a `validatePermission` function to `workflowCommandService.execute()`, and `WorkflowCommandService.execute` treats it as optional: `await definition.validatePermission?.()` (`workflow-command.service.ts:28`) — silently skipped when absent, no error, no log. The port interface itself (`compliance-commands.port.ts:17-22`) has no `actor` parameter on these two method signatures at all, unlike its own `createComplianceRule`/`updateComplianceRule` siblings — the missing check is baked into the abstraction, not just an implementation oversight. `RunComplianceDto`/`ResolveComplianceDto` (`compliance.dto.ts:59-81`) carry no actor field either. Confirmed end-to-end on the frontend too: `apps/event/src/lib/prism-api.ts:604-613`'s `runCompliance`/`resolveCompliance` wrappers call `request(...)` with no `withPmcmActor(...)` — contrast `createComplianceRule`/`updateComplianceRule` two lines below (594-603), which do wrap with `withPmcmActor`. Nobody, frontend or backend, even attempts an identity on these two calls.

**Root cause is shared, not local:** `EventAccessPolicyService.resolveActor` (`event-access-policy.service.ts:34-35`) defaults a missing `actorRole` to `pmcm-admin` — the exact same fail-open shape as EP-05's `plans.service.ts:assertCanUpdatePlan` (PA-145), except this one lives in the shared access-control service every module (including compliance-ops) calls into. Compliance-ops isn't independently broken here so much as inheriting a fail-open default from its dependency — worth flagging at the shared-service level, not just per-endpoint.

## Cross-epic dependency check — floor plan readiness trustworthiness (PA-145 follow-through)

**Confirmed as the audit brief anticipated.** `defenseReadiness`'s floor-plan sub-check reads `floorPlanDrafts.find((draft) => draft.status === 'approved')` — it inspects only the `OpsFloorPlanDraft.status` field, never the underlying `FloorPlan.objects` content or a content-hash/timestamp that would detect tampering. EP-05's PA-145 established that `plans.service.ts:assertCanUpdatePlan` is fail-open for any role other than the literal `'client'` string and never touches `OpsFloorPlanDraft.status` when it mutates plan content. The two facts compose directly: a floor plan's actual layout can be silently altered after approval via `PUT /api/plans/:planId` by a supplier, coordinator, guest, or unauthenticated caller, while `status` stays `'approved'` — so a "Ready"-leaning readiness signal from this composition can be reporting on floor plan content that no longer matches what was actually approved. See PA-159.
