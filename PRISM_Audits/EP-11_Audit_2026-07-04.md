## Executive summary

**This is the most severe audit result of the initiative so far on raw exploitability, and it reopens a finding the tracker likely believes is historical.** `OpsEventCoordinatorAssignmentsController` (`event-coordinator-assignments.controller.ts`) — the controller backing both coordinator assignment creation and acknowledgment — has **zero actor resolution and zero role check of any kind**, not a fail-open default, an actual absence of any auth call. This is exactly the defect EP-02's original 2026-07-02 audit flagged as PA-135/PA-136 ("unauthenticated coordinator assignment/acknowledge endpoints"). Read today, two days later, the same controller is byte-for-byte the same shape: still no `EventAccessPolicyService`, still no actor check. **PA-135/136 is confirmed still open and unpatched**, and EP-11-S01 — the story whose entire AC is built on top of this exact acknowledgment endpoint — inherits the defect wholesale.

**Separately, live-ops has its own, different-shaped version of the shared fail-open problem, and it is the first time this initiative that the fail-open default has been confirmed to grant a working exploit rather than being screened out by a narrower allow-list.** `EventLiveOpsCommandService.requireEventDayWriteActor` (used by event-day task creation/update/escalation, urgent issue creation/update/escalation, and coordinator attendance marking) does call `resolveActor` then `requireActorRole([PmcmAdmin, System, Coordinator])` — a real check exists. But `resolveActor`'s documented fail-open default (a missing `actorRole` silently becomes `pmcm-admin`) is itself one of this allow-list's permitted roles. A caller who supplies **no actor information at all** is granted `pmcm-admin` and sails through the check — meaning any of these coordinator/PMCM-shared live-ops write actions can be performed by a fully anonymous caller with zero query parameters. Compounding this: even when an actor *does* supply `actorRole=coordinator`, the coordinator-attendance-marking path never verifies that the URL's `assignmentId` belongs to that coordinator's own resolved assignment — a real IDOR independent of the fail-open issue. Two independent, unauthenticated ways exist to mark any coordinator present/late/absent on any event.

**Under that severity, the actual coordinator-facing feature work is a mixed, genuinely useful picture the tracker's flat 0% badly understates.** A real "Staffing summary" gap-warning widget exists (EP-11-S04) and mostly works, except it miscounts Pending Acknowledgment coordinators as covering headcount — the exact FAIL trigger named in this story's AC. EP-11-S02 and EP-11-S03's backend logic (event-day tasks, urgent issues, attendance-driven reliability notes) is real, tested against real data shapes, and functionally solid — but none of it is exposed to coordinators in the frontend at all. Every write path is invoked exclusively from the PMCM side under a hardcoded `"Ms. Mys"` actor identity; coordinators can only read role-scoped data, never log their own tasks, issues, or attendance. And EP-11-S05's "five coordinator role views" don't exist as five views — there is exactly one generic `CoordinatorView` component serving every role identically (bar one conditional branch for registration-role guest counts), none of packages/ui's three required shared elements were extracted first as the locked build sequence requires, and none of the three named cross-role behaviors (EDSO+Ms. Mys thread scoping, 15-minute late threshold, 2-minute auto-approval) exist anywhere in code.

A dispatched `ecc:silent-failure-hunter` pass additionally found that the acknowledgment button's primary API call is unguarded (a coordinator gets no feedback at all if acknowledgment silently fails), and that most of live-ops's write methods skip the same-transaction side-effect mode used elsewhere, so a reliability-note/audit/notification failure after a successful DB write surfaces as a hard error to the caller while the underlying state change has already persisted.

| Non-coordinator actors denied | **FAIL — the strongest possible form of this failure** | Since the controller performs no actor resolution or role check at all, this isn't "wrong role gets through" — literally any caller, authenticated or not, coordinator or not, can call this endpoint. **New finding — PA-191 (CRITICAL):** `OpsEventCoordinatorAssignmentsController`'s `assignCoordinator` and `acknowledgeCoordinator` endpoints (`event-coordinator-assignments.controller.ts`) have zero actor resolution and zero role check — confirmed unchanged from EP-02's original 2026-07-02 finding (PA-135/PA-136). Any caller can create a coordinator assignment for any event, or acknowledge any assignment by ID, with no credentials. This is the same "skips the shared resolver entirely" failure mode already documented for `OpsSupplierPareController`/`PA-162` in EP-07 Chain A, now confirmed as a second, still-unpatched instance, specifically load-bearing for EP-11-S01's own AC.

**New finding — PA-192 (HIGH):** `acknowledgeCoordinator` has no precondition on the assignment's current status. A `replaced` (and, were it ever reachable, `cancelled`) assignment can still be acknowledged, both because the backend write is unconditional and because the frontend "Acknowledge role" button is only disabled for the already-`acknowledged` case, not for `replaced`.

**New finding — PA-197 (HIGH), via `ecc:silent-failure-hunter`:** `coordinator-view.tsx`'s `ack()` function (`:243-262`) only wraps the *inner* role-view refresh call in a try/catch — the primary `await prismApi.acknowledgeCoordinator(event.id, assignment.id)` call is unguarded. If it rejects (network error, or the 404-masking issue in PA-198 below), the exception becomes an unhandled rejection out of the `onClick` handler; `finally { setBusy(false) }` still re-enables the button, but no `setError`/toast/visible state ever tells the coordinator whether PMCM actually received the acknowledgment. A coordinator clicking "Acknowledge role" during a transient failure has no way to know they need to retry.

**Completion estimate: ~40%.** The acknowledgment flow works end-to-end for the honest, single intended path (a real coordinator, using the real UI, acknowledging their own current assignment) — and the dashboard-transition wiring behind it is genuinely correct, not two disconnected stores. But every one of this story's own stated FAIL triggers is met: identity isn't verified, non-coordinators aren't denied, withdrawn assignments remain acknowledgeable, and a failure gives no feedback at all.

## Cross-cutting: resolveActor sweep (staffing-ops and live-ops, both new module sweeps)

Two distinct patterns found, not one:

**staffing-ops's write controller skips the resolver entirely.** `OpsEventCoordinatorAssignmentsController` (`assignCoordinator`, `acknowledgeCoordinator`) never calls `resolveActor` at all — the same failure mode as `OpsSupplierPareController`/PA-162 (EP-07 Chain A), and in this case a direct, unpatched continuation of EP-02's own PA-135/PA-136. staffing-ops's *read* controllers (`OpsCoordinatorsController`, `OpsCoordinatorWorkspaceController`) do call `resolveActor` and an explicit role check correctly — the module is split between a guarded read side and an entirely unguarded write side.

**live-ops calls resolveActor and an explicit role check everywhere, but the check is satisfiable by doing nothing.** `EventLiveOpsReadService`/`EventLiveOpsCommandService`'s `requireEventDayWriteActor` and equivalents all call `resolveActor` then `requireActorRole` against an allow-list that includes `PmcmAdmin` — and `resolveActor`'s documented fail-open default (missing `actorRole` → `pmcm-admin`) is itself a member of that allow-list. This is a materially different situation from the "guarded, not exploited" instances logged for EP-07/EP-08/EP-09, where the allow-lists checked were role-specific (client-only, supplier-only) and did not include the fail-open default's granted role — so omitting `actorRole` there gets rejected, not admitted. Here, omitting it is admitted. **This audit did not re-examine every previously-logged "guarded" module's specific allow-list membership** — this finding is scoped to live-ops, not a retroactive claim about EP-05 through EP-10. But it is worth flagging clearly: wherever a module's allow-list includes `PmcmAdmin`, the shared fail-open default is not merely latent risk, it is a working, credential-free path in, and a full sweep of which "guarded" modules' allow-lists include `PmcmAdmin` (almost certainly most of them, since PMCM Admin needs broad access) would be a valuable follow-up, not assumed complete here.

**New finding — PA-193 (CRITICAL):** `requireEventDayWriteActor`'s allow-list includes `PmcmAdmin`, and `resolveActor`'s fail-open default grants `pmcm-admin` to any caller omitting `actorRole`. Combined with EP-11-S03's attendance-ownership gap (above), this means: (1) a fully anonymous caller (zero query parameters) can create/update/escalate event-day tasks and urgent issues, mark any coordinator's attendance, and (via `replaceCoordinatorAssignment`'s identical own `resolveActor`+`requireActorRole([PmcmAdmin, System])` call, `event-live-ops-command.service.ts:124-130`) replace any coordinator's assignment on any event — no credentials of any kind required; and (2) even a caller who does supply `actorRole=coordinator` can mark a different coordinator's attendance via the IDOR already described under EP-11-S03. This is assessed as the most severe finding of this initiative to date on pure exploitability grounds — it requires no forged identity, no IDOR chaining, just an empty query string.

## Cross-cutting: hardcoded-actor-identity check (first coordinator-side test of this pattern)

Per the brief's request to check whether the previously PMCM-admin-only hardcoded-identity pattern (EP-01, EP-04/PA-142, EP-07/PA-171) recurs on the coordinator-identity side: **it does not recur as a coordinator-side defect, because there is no coordinator-side call site to have the defect** — every live-ops write that conceptually belongs to a coordinator (log a task, log an issue, mark attendance) is invoked exclusively from the PMCM side, using the same hardcoded `"Ms. Mys"` actor (`apps/event/src/lib/prism-api.ts:400-405`, `withPmcmActor`) already documented for other PMCM actions. This is a **fourth confirmed instance** of the hardcoded-actor-identity pattern, but it's the same PMCM-side instance recurring across more call sites (event-day tasks, urgent issues, attendance, escalations, coordinator replacement), not a new coordinator-side variant. Where a genuine coordinator-side call exists (`coordinatorRoleView`, the acknowledge flow's *frontend* intent), identity is correctly derived from the real signed-in session (`withCoordinatorActor`, `prism-api.ts:388-398`, using `session.name`/`session.email`) — clean, not hardcoded. The acknowledge *endpoint itself*, however, accepts no identity input at all (see EP-11-S01/PA-191), so this one call site is worse than hardcoded — it's absent.

**New finding — PA-194 (HIGH):** No coordinator-facing UI exists to log event-day tasks, log urgent issues, or mark own attendance — all three write paths are PMCM-only, under the hardcoded `"Ms. Mys"` actor identity, continuing the established hardcoded-actor-identity pattern onto three additional call sites.

## Silent-failure findings (via `ecc:silent-failure-hunter` subagent, EP-11 staffing-ops/live-ops surface)

Five concrete findings, folded into the PA list above where they affect a specific story's AC (PA-197), plus two broader ones kept here since they cut across multiple write paths rather than one story:

- **`coordinators.service.ts:230-238`** (acknowledgeCoordinator's `write()`): `.catch(() => { throw new NotFoundException(...) })` converts *any* Prisma error (connection loss, constraint violation, timeout) into a misleading 404, discarding the real error. A coordinator/PMCM sees "assignment not found" even when the assignment exists and the real cause was an infra failure. MEDIUM, not separately numbered — a refinement of the same endpoint already covered by PA-191/PA-192.
- **New finding — PA-198 (MEDIUM):** `updateCoordinatorAttendance` and `replaceCoordinatorAssignment` (`live-operations.service.ts:447-643`), and the entire event-day-task/urgent-issue create/update/escalate surface in the same file, do not set `sideEffectMode: 'same_tx'` (unlike `coordinators.service.ts`'s `assignCoordinator`, which does). Per `WorkflowCommandService.execute` (`workflow-command.service.ts:37-40`), only `same_tx` calls wrap `write()` and `sideEffects()` in one transaction — otherwise `write()` commits immediately and `sideEffects()` (reliability-note creation, audit write, event-day log, notification queue) run afterward, uncommitted-together. If a side effect throws, the caller sees a hard failure while the underlying state change (attendance marked, coordinator replaced, task/issue created) has already persisted — and because none of these calls carry an idempotency key (unlike `assignCoordinator`, which does), a caller who retries after seeing that failure can create a duplicate reliability note or a second replacement chain.
- Additionally noted, not separately numbered: `EventDashboardClient.tsx:1572`'s post-assign command-data refresh (`.catch(() => undefined)`) silently swallows any refresh failure after a successful `onAssign` — no error surfaces, but dependent staffing/command views can go stale with zero indication. Same shape as EP-10's PA-187 finding, recurring in a different component.
