## Priority Check — is EP-04-S01's upload path the EP-01-S03 finding?

**Yes, definitively the same function, unchanged.**

- Controller: `apps/api/libs/modules/inquiry-onboarding/src/controllers/inquiries.controller.ts:58-61` — `uploadConforme(@Param('inquiryId') inquiryId, @Body() dto: UploadConformeDto)`. No actor/query parameter of any kind.
- Passthrough: `apps/api/libs/modules/inquiry-onboarding/src/services/inquiry-workflow.service.ts:103-110` — calls `context.inquiriesService.uploadConforme(inquiryId, input)` directly. No `resolveActor`/`requireActorRole` call, unlike the two sibling methods in the same file (`listInquiries:46-48`, `listOnboarding:58-60`), both of which do call `requireActorRole`.
- Implementation: `apps/api/libs/modules/inquiry-onboarding/src/services/inquiries.service.ts:208-437` — same line range EP-01-S03 cited on 2026-07-02. Confirmed byte-for-byte the same defect one day later: no `validatePermission` hook is set in the `WorkflowCommandService.execute()` command definition (compare `workflow-command.service.ts:14,28`, which supports one — it is simply never wired here).

This is the exact endpoint EP-04-S01 AC-1 names as "the inquiry-onboarding module uploadConforme path." Per the requested framing: this is a **CRITICAL finding** — the missing-role-check pattern already confirmed in EP-01 (uploadConforme itself), EP-02 (coordinator assignment/acknowledge endpoints), and EP-03 (submitBriefing) is now confirmed to sit directly underneath the project's stated **highest-priority story** (`handoffs_archive/AC_Tracker_Phase2_Output.md:423`: "HIGHEST PRIORITY C2 DELIVERY — 10 downstream stories gate on this"). It is not a new, independent occurrence of the pattern — it is the same unpatched code EP-01-S03 already flagged — but EP-04-S01's own AC-1 ("blocks non-PMCM actors" is implied by "PMCM Admin can upload") and AC-9 (audit identity) both fail as a direct consequence, and no fix has landed in the day since it was first reported.

**Contrast:** every read-side endpoint touching the same `OpsDocument` data (`pmcm-dashboard.controller.ts` → `event-read-models.service.ts:778-779,835-836` for PMCM, `client-workspace.controller.ts` → `event-read-models.service.ts:308` for Client) is correctly role-gated via `requireActorRole`. The write path that actually performs the highest-stakes state transition in the whole system (unlock client portal, generate billing, activate event workspace) is the one left unguarded.

## PA-109 — does uploadConforme call billing logic directly, or route through FinanceOpsModule?

**Resolved: directly, not through FinanceOpsModule.**

- `apps/api/libs/modules/inquiry-onboarding/src/services/inquiries.service.ts` has zero import of `@prism/modules/finance-ops` or `BillingOperationsService` anywhere in the file (confirmed via grep, no matches).
- Billing statement, billing source, and payment milestone creation happen inline inside `uploadConforme`'s own `this.prisma.$transaction(...)` callback, using raw `tx.opsBillingStatement.create` / `tx.opsBillingSource.create` / `tx.opsPaymentMilestone.createMany` at `inquiries.service.ts:339-403`.
- The actual finance port, `BillingOperationsService.generateBillingStatement`, lives at `apps/api/libs/modules/finance-ops/src/services/billing-operations.service.ts:356` and is invoked from a completely separate call path (`apps/event/src/app/dashboard/EventDashboardClient.tsx:2674` → `prismApi.generateBillingStatement`, PMCM-manual "Generate billing statement" action in the closure workspace). `uploadConforme` never touches this service.

This confirms the same conclusion already recorded informally in `handoffs_archive/PRISM_Francis_EP02S05_PostBuild_Handoff_v1.md:37,110` ("uploadConforme creates billing records directly inside InquiriesService, not behind FinanceOpsModule... functionally works but ownership not clean") — still true, unchanged, as of 2026-07-03. **This blocks the EP-08-S01 Done call as the tracker already notes**, and that gate is legitimate: the coupling is real and unresolved, not a stale concern.
